# Architecture

This document describes how Web Remote Manager PRO (WRM) is built. It is the result of
"Step 0 — repo audit" of the extension plan (WRM as a lightweight PAM for teams), and it maps
every phase of that plan to the code that it touches.

## Stack

| Part | What it is |
|---|---|
| Backend | **Go** (version in `remote-manager/go.mod`), standard library `net/http`, no web framework. One self-contained binary. |
| Libraries | `golang.org/x/crypto/ssh` (SSH client), `github.com/pkg/sftp`, `github.com/jlaffaye/ftp`, `github.com/gorilla/websocket`, `github.com/pion/turn/v4` (TURN relay for voice), `modernc.org/sqlite` (pure-Go SQLite, no CGO), `rsc.io/qr` |
| Frontend | One page, `remote-manager/static/index.html`: plain JavaScript, no framework, no build step. `xterm.js` and fonts are vendored in `static/vendor/`. Everything under `static/` is embedded into the binary with `go:embed`. |
| Database | SQLite in WAL mode (`DB_PATH`, default `./remote_manager.db`), mode `0600`. |
| Build / run | `go build`; CI (`.github/workflows/build.yml`) runs gofmt, vet, tests with the race detector, a JS syntax check, cross-compiles 13 targets and publishes releases on tags. Security checks (v12.6.20): `security.yml` (govulncheck, staticcheck, gosec against `.github/security/gosec-baseline.json`, gitleaks, actionlint/zizmor, dependency review), `codeql.yml`, `scorecard.yml`, `claude-security-review.yml`, Trivy in the Docker job, Dependabot; `nightly.yml` (v12.6.21: Go fuzzing of the import parsers, OWASP ZAP). Releases: `SHA256SUMS.txt` signed with ed25519 (`releasesign.go`, checked by the self-update), CycloneDX SBOM, build provenance; all actions pinned to commit SHAs with read-only tokens by default. `Dockerfile` + `docker-compose.yml` for container deployments. |

## Log discovery and journal sources (v13.0)

`POST /api/monitoring/logs/discover?id=` is the only entry point that scans a host, and only the connection owner can call it. `monitorDiscoverRoots` builds two things in one pass: log roots (folders and journal units) and a service inventory (`monitorServiceInfo`), so a service whose output never reaches a file is still visible with the reason. Sources are all read-only file reads, no remote command runs during discovery: configured roots, stored Git installs, systemd unit files under `/etc/systemd/system`, `/usr/lib/systemd/system` and `/lib/systemd/system` (`StandardOutput`/`StandardError` `append:`/`file:`/`truncate:` targets, plus `WorkingDirectory/{log,logs,var/log,var/logs}`), Supervisor program blocks, Docker `containers/*/config.v2.json` (`Name`, `LogPath`; no Docker socket) and the bounded operator/service folder walk over `/home/<operator>`, `/srv`, `/opt` and the configured server roots. The result is cached for one hour bound to owner and configuration; `GET /api/monitoring/logs` only lists files from that cache and reports `discovered: false` when nothing was scanned, so opening the tab cannot start a scan. `monitorLogDirName` accepts `log`, `logs`, `log-*`, `logs_*`, `*-log`, `*_logs` and deliberately not `catalog`, `dialog` or `blog`.

A root with `kind: journal` stores `unit` and a canonical `journal:<unit>` path. `monitorJournalLogHandler` reads it with `journalctl --no-pager --output=short-iso --unit=<unit> --lines=N --since=@<unix> --until=@<unix>`: the unit must match `monitorJournalUnit`, timestamps are formatted from parsed values and no request text reaches the shell. Reading uses the same `PermFilesRead` check and SSH account as a file read, so the OS still decides journal visibility. The chunk reports `kind: journal` and carries no byte offsets; live following sends `since` from the last entry time instead of a byte offset. Discovery is audited as `monitor.logs_discovered`; shares may read a journal source but cannot trigger a scan.

The assistant uses the same inventory instead of guessing paths (`ai_logs.go`): `find_logs` lists the services with their folders or journal unit, and `read_log` opens one service's newest log file (`service`, or an explicit `path`) with an optional literal `grep`, or its journal unit. Both are read tools, so `aiEvaluate` allows them in read-only mode, the `read_logs` scope covers MCP clients, output is redacted and size-limited and every call is audited like any other read. `aiLogSource` reuses the one-hour cache the Logs tab filled; without a cache the connection owner gets one scan over the session's own SSH client (no second connection, no shell command), while a share is told to run Find logs first.

## Monitored services (v13.1)

`monitorConfig.Services` lists up to 20 `{kind, name}` entries, written in **Monitoring settings** (`PUT /api/monitoring/config?id=`). `normalize` accepts only `systemd` units and `docker` container names against strict patterns, so nothing else reaches the host. When the transport is `ssh`, `collectMonitor` runs one extra command on the same connection after the metrics: `monitorServiceScript` is a fixed POSIX `while read` loop whose heredoc carries the validated names on stdin, and it prints one `kind:name=state` line per service (`systemctl is-active` for units, `docker inspect -f '{{.State.Status}}'` for containers, `missing` when the container does not exist). `parseMonitorServiceStates` reads those lines into `monitorSample.Services`, and `monitorServiceProblem` escalates a healthy sample to `problem` with a `service problem: …` message when any watched service is not `active`/`running`; `pollMonitor`'s existing transition notification then reports the failure and the recovery. The `direct` and `api` transports have no shell, so a service list applies to SSH monitoring only, and the UI says so.

`card()` renders the states with `ok`/`bad` pills and carries a **Poll automatically** checkbox that writes the whole profile back through the same endpoint; the settings dialog gained the matching textarea (`systemd:nginx`, `docker:web`, one per line).

## Community library (v13.1)

`addons_community.go` reads the index of the public repository "WRM Pro - community public addons" (`addonCommunityIndex`, `GET /api/addons/community`, cached for ten minutes). An entry carries `id`, `name`, `version`, `license`, `capabilities`, `trust`, `url` and `sha256`; `addonCommunityValid` keeps only entries whose trust is known, whose checksum is 64 hex characters, whose capabilities exist in this build and whose `url` points at `github.com`, `raw.githubusercontent.com`, `objects.githubusercontent.com` or `codeload.github.com` over HTTPS (loopback HTTP is accepted for the tests). One malformed entry is dropped instead of failing the whole index.

`POST /api/addons/community/install` is administrator only. It downloads the ZIP (20 MB cap, five redirects), compares the SHA-256 with the index and refuses with 409 without writing anything on a mismatch; a match is handed to `addonInstallBytes`, the same function the upload endpoint uses after reading the body, so the manifest, entry names, capabilities, declared files and server module are checked exactly once in one place. The source is stored as `community:<id>@<trust>` and the install is audited as `addon.installed`. The pane renders the trust badge and the index's explanation of that level, and the existing community/no-warranty notice sits above it.

## Addons (v13.0)

An addon is a folder that is dropped in and discovered at runtime, never compiled into the binary: `<DB_PATH>.addons/<id>/addon.json` plus the files it declares, installed from a ZIP through `POST /api/addons/install` (administrator only, 20 MB and 500 files at most). `addonReadArchive` validates before anything is written: entry names must be relative, unique (case-insensitively) and free of `..`/backslashes, `addon.json` may sit at the root or one folder down, only `addon.json`, a panel `.html` and a theme `.css` are declared, and a declared file missing from the archive refuses the install. The manifest's `capabilities` are checked against `addonCapabilities` — this build implements `ui.panel` and `ui.theme` — so an unknown capability or a `server` block refuses the archive instead of being silently ignored. Files are unpacked into a temporary folder inside the addons root and swapped in with a rename that keeps the enabled state; the SHA-256 of the archive and the manifest JSON are stored in the `addons` table.

`GET /api/addons` lists the addons (non-administrators see enabled ones only), `POST /api/addons/{id}/enable|disable`, `DELETE /api/addons/{id}` and `GET /api/addons/{id}/asset/{file}` serve the files. Assets are limited to known types (`html css js json svg png jpg gif webp ico woff2 txt`), resolved inside the addon folder only, sent with `nosniff` and `X-Frame-Options: SAMEORIGIN`; HTML carries `Content-Security-Policy: sandbox allow-scripts`. Every install, enable, disable and removal writes an audit entry (`addon.installed`, `addon.enabled`, `addon.disabled`, `addon.removed`) with the version, capabilities and checksum.

`static/addons.js` is the client: Settings → Addons lists the addons and installs a ZIP, an enabled `ui.theme` is one `<link>` on `<head>` that is removed when the addon is disabled, and an enabled `ui.panel` opens as an ordinary WRM window (`mode: 'addon-panel'`) whose content is an `iframe` with `sandbox="allow-scripts"` and no `allow-same-origin`. The panel therefore has an opaque origin: it cannot read the page, its DOM, cookies or another panel. The only data it gets is a `postMessage` context (the display name, never the sign-in name; language, theme tokens, connection names/hosts/ports) resent on request, and the only messages accepted back are `wrm:notify` (a toast) and `wrm:context`. The pane also generates the **AI addon** prompt from `addonCapabilities`, so the text can only describe hooks this build implements: it is copied into the user's AI client or handed to the built-in assistant, and whatever comes back still goes through the ZIP installer and its checks.

## Addon drafts and the AI tools (v13.3)

The assistant writes addons into `<DB_PATH>.addons/.drafts/<id>/` (`addons_drafts.go`), never into the live folder. `addonDraftSave` builds the new state in a temporary folder inside the drafts root, copies the existing draft first when the call is an `addon_write`, writes the given files, then validates the result with `addonDraftValidate`: `addonDraftZip` produces the same archive an upload would carry, `addonReadArchive` applies the manifest, layout and declared-file checks, and `addonCheckWASM` compiles server code without running it. Only a valid draft replaces the previous one, so a broken write changes nothing. Draft ids and paths use `addonIDPattern`/`addonSafeRel`; a draft is never served by the asset endpoint and never executed.

`GET /api/addons/drafts` lists the drafts with their files, manifest, validity and installed version; `GET /api/addons/drafts/{id}/diff` returns a unified diff against the installed addon (`addonDraftDiff`); `POST /api/addons/drafts/{id}/install` zips the folder and calls `addonInstallArchive`, the same function behind an uploaded ZIP and the community library; `DELETE /api/addons/drafts/{id}` discards the workspace copy. A new addon is installed disabled, and an update keeps the enabled state it already had: no draft install enables anything. The pane (`static/addons.js`) shows the drafts above the installed list with **Diff**, **Install draft** and **Discard**.

The AI tools are `addon_list`, `addon_files`, `addon_create`, `addon_write`, `addon_enable`, `addon_disable`, `addon_delete`, `addon_run` and `addon_install_community` (`ai_addons.go`). They are marked `Host` in `aiToolSpec` because they act on WRM itself, not on the session's server, and they require the `addons.manage` MCP scope. `CallTool` refuses them for a non-administrator even when the token carries the scope, `aiToolDefsForUser` and `mcpToolList` hide them from non-administrators, and `mcpGrantRequest.validate` refuses `addons.manage` for a non-administrator. Every write and `addon_run` is forced to `approve` after the normal policy decision, so automatic mode and full access still ask; a read-only session refuses them. `addon_run` calls `addonCallWASM` only for an enabled addon and a declared export.

Server code is a WebAssembly module (`addons_runner.go`), never a native binary or a shell script. `wazero` creates one runtime per process with `WithCloseOnContextDone(true)` and `WithMemoryLimitPages(1024)`; a call compiles the declared module, instantiates it fresh and closes both, under a five second context. No WASI is instantiated, so a module that imports anything but `wrm.log` fails to start rather than reaching a host resource; there is no filesystem, network, environment, clock or random source. The ABI is deliberately small: the host calls `wrm_alloc(size) -> ptr`, writes the JSON request there, calls the declared export `(ptr, len) -> ptr` and reads a NUL-terminated UTF-8 result (1 MB cap) from that pointer. Input is capped at 64 KB and the module file at 8 MB. Install compiles the module without running it (`addonCheckWASM`) and refuses one that is invalid, does not export `wrm_alloc` or its memory, misses a declared export, or imports anything but `wrm.log`. `POST /api/addons/{id}/call/{export}` is administrator only, requires the addon to be enabled and the export to be declared in the manifest, and writes `addon.call` to the audit log; the settings pane exposes the same call with an input box. The community library (`addons_community.go`) reads the public index, keeps only entries from HTTPS GitHub hosts with a known trust level and a matching SHA-256, and hands a verified download to `addonInstallArchive`.

## Docker for Medium (v12.6.6)

`git_medium_ca.go` gives Medium's containers the host's trust: `mediumWriteCABundle` collects the host's roots (`mediumHostRoots`: the Windows ROOT stores through `CertEnumCertificatesInStore`, `security find-certificate` on macOS, the CA bundle elsewhere; policy `medium_host_ca`) and `medium_ca_file` into `<DB>.medium/host-ca.pem` at runtime preparation and at each start; `mediumCAArgs` mounts it read-only and sets the CA environment, and `mediumCACommand` makes `/bin/sh` concatenate it with the image's bundle into `/tmp/wrm-ca.pem` before it execs the real entrypoint. `git_medium_docker.go` decides how this host gets Docker (`mediumDockerInfoNow`, cached for a minute while Docker is missing because finding the privileges runs `sudo -n true`): Linux uses the distribution's packages (`mediumLinuxPlan`: apt `docker.io`, Fedora `moby-engine`, Docker's `docker-ce` repository on RHEL-like systems, zypper/pacman/apk) and its service manager; macOS and Windows use Docker Desktop from `desktop.docker.com`. `mediumPrivilege` picks how commands run as root: directly, through `systemd-run --wait --pipe` when WRM is root inside its own sandboxed unit (`INVOCATION_ID`; the transient unit is outside `ProtectSystem=strict` and `NoNewPrivileges`), through passwordless `sudo -n`, or not at all, in which case the status names `wrm -setup-docker` (`runSetupDocker`, Linux, as root: install, start, `usermod -aG docker` for the unit's `User=`, `systemctl try-restart`). Installation needs the `medium_docker_install` policy and an administrator's consent (`<DB_PATH>.medium/docker-consent.json`, written by `POST /api/git/medium/docker` with an audit row; Docker Desktop also needs `accept_license`). `mediumEnsureDocker(ctx, step)` installs when the CLI is missing, reports a socket that refuses WRM's account, starts Docker Desktop (`docker desktop start`, `open -a`, `Start-Process`) or the engine's service, and waits `mediumDockerWait`; every command goes through `mediumCommand`, so its output is in the operation's ring buffer and the activity log. Downloads only follow redirects within docker.com and are bounded to 2 GiB; Windows checks the Authenticode signer (O=Docker Inc) before `install --user --quiet --accept-license --backend=wsl-2`, macOS `codesign --verify --deep --strict` and team `9BNSXJN65R` before `install --accept-license --user=<console user>` (or a copy to `~/Applications` without rights). `mediumSelectBackend` now prefers Docker on Linux and macOS too, except where the host runtime was prepared and the Docker runtime (`docker-ready`) never was, and on systems without Docker. `sudo -n true` is probed once per process (again when an administrator presses Install Docker), proxy variables are passed through `systemd-run --setenv` and `sudo -n -- env`, and the installation runs on a detached 45-minute context so the operation deadline never kills a package manager. Docker commands get the CLI's directory on `PATH` for Docker Desktop's credential helper.

## Medium operations, steps and activity (v12.6.5)

`git_medium_activity.go` wraps every operation that takes the global `mediumOperation` lock (setup, prepare, tool import, start, config/SSH apply) in `mediumBeginOp` / `mediumEndOp`: `TryLock`, a holder (`mediumOps.holder`: op, user, start) that `GET /api/git/medium` reports to everyone and the `409` text names, a reset of the caller's step list, a `running` row in `medium_activity` and a console line; the end closes the last step, records status, duration, steps (JSON) and output, prunes to 1000 rows per user (shared rows separately), then clears `Busy`, the holder and the lock together. `mediumSetStage` appends steps (start time, duration, error) to the user's `mediumStatus` and notes them in the operation's output. `mediumCommand` and the original process write into `mediumRing` buffers (200 lines); `Tail` redacts with `redactText`, and stored output is encrypted with `encryptValue`. `mediumOutputVisible` applies `medium_log_output`: owner and administrators, and every Medium user for shared rows (preparation and tool import). Rows left `running` by a restart are marked `interrupted` at startup.

`/start` and the tool import run in goroutines that own the operation handle and return `202`. A deploy-config ZIP is validated with `mdLoadConfig` before anything else; when the runtime is not ready, the tool runs or the lock is held, config and SSH ZIPs are stored as `pending-config` / `pending-ssh` (`mediumKeepPending`, renames under `mediumPendingMu`) and `mediumApplyPending` renames each to a `.applying` snapshot, validates it with the original tool and applies it at the next start or setup; a rejected config is discarded, a check that could not run (Docker down, timeout) puts the snapshot back unless a newer ZIP arrived. The native preview reads a kept config first (`mdConfigDir`). `ready` in the status turns true only when the process answers its readiness probe. The process's `Wait` goroutine records `last_exit` and an `exited` activity row for an unexpected exit after readiness. `static/git.js` renders the guide from the status (`mediumPaintSteps`, `mediumHint` per failed step), polls every 2 seconds while an operation runs and shows the activity log (`mediumActivity`).

## Dialog history, partial stamps and Medium locking (v12.5.0)

`static/git.js` `modal()` keeps the dialog element it replaces (DOM, values and handlers) on a bounded trail when the new dialog has a different title and the old one has content; transient loading/error dialogs and re-renders of the same dialog are not kept. `modalBack()` reattaches the previous element; `closeModal()` clears the trail. `index.html` `openInsteadOf(from, open, reopen)` gives a dialog opened in place of another a Back button that reopens the opener (Settings keeps its tab).

Stamp (`stampItem`) refuses installations that are not up to date unless `stamp_partial` is set; VERSION.md then uses `versionRows` (older files carry their matching version, changed files `(local)`, missing files are left out) and an extra `Napomena` field that `parseVersionMD` ignores.

Medium starts are serialized per user (`mediumStartLock`); `mediumMgr.mu` only guards the process map, so status, proxy and Stop do not wait for Docker sync or readiness. `/stop` runs before the global setup lock. Log scans keep raw bytes for offsets, end at the last complete line and replace invalid UTF-8 only in returned lines.

## Medium setup and log workflows (v12.4.5)

`git_medium_setup.go` handles a single bounded multipart setup request. ZIPs are extracted/validated before replacement, retained privately, and a serialized background job starts Docker, prepares the original runtime, validates pending config/SSH, records revisions and launches the original proxy. Runtime errors preserve pending imports; an explicitly uploaded local config clears its older config-Git override. Docker installation (v12.6.6, `git_medium_docker.go`, see above) downloads only from HTTPS Docker domains, bounds size and verifies the Docker Inc. signature before running the vendor installer; it accepts Docker Desktop's licence only after an administrator did so in WRM. No reboot, Docker context change or container-engine switch is performed. Existing individual setup routes remain.

`monitoring_discovery.go` combines configured roots, stored installation log folders, bounded service/operator-directory metadata and bounded Supervisor metadata. A one-hour owner/config-bound memory catalog permits reads of discovered roots; current connection permissions and safe paths remain checked on every read. Directory entries identify regular log-like files without per-file REALPATH calls; content reads still reject every symlink component. Root changes invalidate prior catalogs. No discovery executes scripts or full Git comparisons.

Monitoring UI publishes each server independently with cancellation/version guards. Cross-file search uses the existing historical byte cursor with three workers, per-file 32 MiB/64-request and round 90-second limits, explicit continuation and 256 KiB excerpts. File modification/event-range metadata remains distinct. Sticky stacks contain filters plus check/action controls; Environment filters share cached/deduplicated cell reads.

## Managed Medium runtime (v12.4.3b)

`git_medium_runtime.go` selects Docker on Windows and optionally on Linux. Approved source imports are retained independently of preparation; a pending marker prevents false readiness and an administrator can retry setup. CLI discovery preserves host Docker context and supports standard Windows install locations. The pinned Linux image supplies runtime dependencies; a Linux volume holds its venv and per-user named Linux volumes retain native data/permissions. Only explicit config/SSH revisions are copied into an existing user volume. Runtime source/venv are read-only; no Docker socket or other users' volumes are mounted.

Container environment aliases are translated by the embedded wrapper before original imports, leaving the Docker CLI's host HOME intact. A private SSH-home link makes OpenSSH's passwd-based tilde expansion work. Private files use a restrictive umask; original builds set their own build umask and drop to an unprivileged account. WRM records source/preparation state, owns random container names, checks readiness/busy and stops only its own processes. Backups include private host data/key plus the named volumes. A local Linux Docker engine is required; remote Docker/Windows Server Desktop are not represented as supported.

## Medium, configuration profiles, Bitwarden and order (v12.4.3)

`git_medium.go` imports an administrator-approved original tool into `<DB_PATH>.medium/tool`, installs pinned Python dependencies in its venv, and starts per-user localhost ASGI processes. Embedded `medium_wrapper.py` authenticates a random private bridge key and exposes readiness/busy probes, then delegates to the unchanged original app. The reverse proxy strips WRM credentials, translates original URL/header roots into `/medium/`, permits same-origin embedding and checks auth/policy/CSRF on each request. Native plans, backups, locks and history remain the original engine's data, separate from existing WRM runs. Config/SSH/data directories are user-specific; preferences are encrypted. This is process/directory separation, not an OS sandbox; editable native commands run as the WRM OS user.

`git_config_profiles.go` adds an owner-scoped `git_config_profiles` table. Uploads use the existing static configuration parser and persist masked/encrypted structured values. Checks resolve owned catalog installations and read only installation-contained paths, with four concurrent reads, a two-minute request deadline and explicit bounds/warnings. The response joins reference/actual values with hostname/connection/service/environment/operator metadata; live remote content is not persisted.

`bitwarden.go` uses the official CLI with isolated per-user appdata. Master/client/session secrets are passed in child environment variables, unlock sessions stay in memory, CLI output is bounded and stderr discarded. The CLI profile is decrypted to mode-0600 `data.json` for a serialized command and re-encrypted/removed afterward; startup protects a plaintext profile left by interruption. Native SSH key IDs are stored in connection options. `resolveConnectionAuth` fetches the native item and parses the private key for existing SSH dialing. The browser receives item metadata only. Idle expiry/logout/restart blocks new retrieval; already authenticated SSH sessions continue.

`folders.sort_order` is an additive migration. Existing zero ranks retain alphabetical ordering; new folders append. Owner-scoped reorder transactions serialize hierarchy changes, validate sibling anchors/cycles/depth and save ranks. Config export/import and pickers preserve the order. UI supports before/after/nested/root drag targets and keyboard-accessible menu actions.

Docker provides optional Python/native SSH/rsync/Git/Bitwarden dependencies. Standalone core functionality remains Go-only; these two integrations need their external runtime tools. See [Medium parity](docs/MEDIUM_PARITY_v12.4.3.md) and [release summary](docs/RELEASE_SUMMARY_v12.4.3.md).

## Service functionality, folder hierarchy and previews (v12.4.0)

`git_functionality.go` extends the existing per-user Git catalog with optional `functionality` units, HTTP/TCP endpoints and config paths. Manual jobs, periodic rounds and post-deploy refreshes store redacted runtime checks in `git_installs.data`; `git_server_health` caches per-user/per-connection Supervisor inventory, failed systemd units and resource checks. `git_scan.go` associates Supervisor stanzas with installations and retains gone installations. Unknown/incomplete checks are explicit, and notifications compare previous state/warnings to avoid repeated identical alerts. Runtime commands do not start/restart services and use the SSH account without automatic sudo. Endpoint probes use SSH `direct-tcpip`, short timeouts, verified TLS and no redirects.

Configuration inspection is an owner/policy-checked on-demand API (`GET /api/git/installs/{id}/configuration`) that reads bounded files inside an installation, parses structured settings/functions and masks sensitive values before sending them to the browser. Raw configuration is not persisted. JSON, INI and assignment-style files are supported; unsupported lines and inspection limits are reported.

`folders.parent_id` is additive. `folders.go` validates ownership, cycles and depth, serializes hierarchy mutations, derives full paths and imports parents before children. Folder deletion reparents children. Shared folder membership uses an owner-scoped recursive CTE; route defaults continue to use the immediate folder. Config export/import preserves old-ID mappings, and new mRemoteNG imports create nested folders. The sidebar renders recursively; folder context is visible in pickers/windows/tabs, with a separate folder row filtering open tabs.

`preview.go` serves authenticated allowlisted remote file previews. SFTP uses a seekable remote file with `http.ServeContent`; FTP uses REST/RETR for range offsets. Text is bounded, active formats use text MIME, and inline responses use nosniff plus a restrictive CSP (sandboxed for non-PDF previews; PDFs use the browser native viewer). File permissions/share roles are checked on every metadata/content/range request. The viewer closes media sources when dismissed. Terminal selection is a filename, resolved against CWD/home, never a shell command.

AI eligibility includes SSH-backed SFTP connections. An always-available account status entry point distinguishes provider connectivity from account policy. `ai_policy_changed` events refresh other browsers and effective policy is refreshed after event-bus reconnect. Backend access checks continue to govern every session/action; terminal AI and MCP setup remain independent.

## Auth model

- Local accounts in `users` (bcrypt cost 12). The first account is the administrator; self-registration is closed by default.
- Sign-in sessions in `auth_sessions`: a random 256-bit token in the `wrm_session` cookie (HttpOnly, SameSite, Secure over HTTPS). Only the SHA-256 of the token is stored. Sessions expire after idle and absolute timeouts (policies).
- Two-factor authentication: TOTP (RFC 6238) with single-use recovery codes; a policy can require it for admins or everyone (`users.go`, `totp.go`).
- Roles (v12.6.23, `roles.go`): `users.is_admin` stays the source of truth for administrators; `users.role` holds `auditor` or `operator` ('' = user). `userRole`/`roleOf` resolve it, `requireAuditRead` lets auditors read audit data, and `policyAllows` evaluates who-policy values (`off`, `admins`, `operators`, `teams:<names>`, `all`; auditors never pass). Teams (`teams.go`) are `teams` and `team_members` (with `lead`); `share_teams` gives a team a role in a share, and `resolveShareAccessCtx` takes the best of the direct and team roles. Step-up: `requireStepUp` answers `403 {step_up: true}` unless `auth_sessions.step_up_at` is within `step_up_minutes` (set at sign-in and by `POST /api/auth/step-up`); the UI's fetch wrapper asks and repeats the request once. Break-glass accounts (`users.break_glass`) are checked against `break_glass_ips` at sign-in. `handOver` moves what a deleted user owns to another account in one transaction. Per-share roles: see Sharing. Policies are in `app_settings` and can be forced with `WRM_<KEY>` environment variables (`settings.go`).
- Directory sign-in (v12.6.24, `oidc.go`, `oidc_jwt.go`): `oidc_providers` holds each identity provider (client secret encrypted, `rules` as JSON); `user_identities` links an account to an immutable directory ID (`tid:oid` or `iss|sub`) with its encrypted refresh token and the last check. `GET /api/auth/oidc/start` keeps the PKCE verifier, nonce and mode in memory (`oidcState`, 10 minutes) and binds the `state` to a cookie; the callback verifies the ID token (`oidcVerifyIDToken`, JWKS cached and refetched on an unknown key), maps claims to a role and teams (`oidcMap`, `oidcApplyMapping`, SSO memberships marked `team_members.source = 'oidc'`) and creates the session with `auth_sessions.identity_id`. Link, step-up and test sign-ins run in a separate window; the page polls `/api/auth/oidc/result`, because the window comes back from another site and COOP separates it from its opener. `oidcRevalidateLoop` refreshes identities that have sessions and ends access on a refused refresh (`oidcEndIdentity`). `localLoginLimited` (`local_login = break_glass` with an enabled provider) gates password sign-in and registration.
- LDAP / Active Directory and SCIM (v12.6.25): `ldap_proto.go` is a small LDAPv3 client (BER, LDAPS or StartTLS, simple bind, paged search, RFC 4515 filter compiler). `ldap_directories` holds each directory (service account password encrypted, `rules` as JSON, last check); `ldap_identities` links an account to a directory's immutable ID (`guid:<hex>` or `<attr>:<value>`). `apiAuthLoginHandler` passes unknown names and directory-linked accounts to `ldapSignIn` (service-account search, user bind, account state, groups through `LDAP_MATCHING_RULE_IN_CHAIN` or a breadth-first walk, `directoryMap` / `directoryApplyMapping` with `team_members.source = 'ldap'`). `ldapSyncLoop` runs `ldapSync` every `ldap_sync_minutes`. `scim.go` serves `/scim/v2` with bearer tokens from `scim_clients` (SHA-256); `scim_users` and `scim_groups` map SCIM IDs to accounts and teams per client, `scim_group_members` holds membership, and `scimSyncUserMapping` applies the client's rules (`source = 'scim'`). `endUserAccess` (`directory.go`) is the one function every deprovisioning route calls.
- SIEM export, alerts and lockdown (v12.6.26): `auditWrite` calls `alertObserve` (a buffered channel to `alertWorker`, which runs the rules in `alertCheck` and writes `security.alert` through `raiseAlert`) and `siemNotify` (wakes `siemLoop`). `siem_destinations` holds each destination (kind, address, `config` JSON, encrypted secret, `cursor` = last audit_log id delivered, counters, last error); `siemRunOnce` reads up to 200 newer audit rows per destination, builds the events (`siemEvent`, identity from `users`, `user_identities` and `ldap_identities`), sends them with `siemSend` and moves the cursor only on success, with a per-destination backoff. The lockdown is the internal setting `_lockdown` (JSON: on, reason, by, at, source) or `WRM_LOCKDOWN`; `lockdownRefuses` is checked in `lookupSession`, `finishLogin`, the OIDC callback, the AI and MCP gates and `resolveShareAccessCtx`, and `lockdownWatchLoop` applies a lockdown set by `wrm -lockdown` or another instance within five seconds. `stopUser` disables the account and calls `endUserAccess`.
- Security levels (v12.6.22, `security_level.go`): `levelRules` holds each level's floor per setting (`levelMeets` compares by an order list or numerically, `Less` for limits where lower is stricter, `ZeroOff` where 0 means no limit). `planLevelChange` builds the preview (changes, env-forced values, blockers such as HTTPS over plain HTTP, affected users and sessions); `enforceSecurityLevel` raises settings except env-locked ones and recorded deviations (table `security_deviations`). `PUT /api/admin/settings` validates all values first and refuses a value below the level without a note in `_deviation_notes`; `settingsChanged` runs the side effects of changed settings. `require_https` refuses password sign-in, registration and 2FA over HTTP except from loopback (`signInTransportError`). `security_posture.go` builds the posture checks for *Admin → Security*.
- CSRF: every non-GET `/api` request needs `X-WRM-Request: 1` and a same-origin `Origin`; WebSockets check `Origin` (`security.go`).
- MCP clients authenticate to `/mcp` only with bearer tokens of AI connections (hashed in `mcp_tokens`, never the session cookie); `/mcp` and the OAuth endpoints check the `Origin` against WRM itself and `ai_mcp_allowed_origins` instead of the CSRF header (see *AI desktop apps / MCP*).
- Request bodies are limited per path (`bodyLimitFor`): 1 MB by default, 32 MB for the import endpoints (`/api/config/import*`, `/api/inventory/*`; files up to `maxImportFile` = 20 MB, the same limit the browser checks), streamed uploads by policy. Import handlers answer HTTP 413 with the size and the limit (`decodeImportJSON`).

## SSH / connection layer

- **Terminal**: `GET /ws/ssh?id=…` (`ssh_ws.go`). WRM opens the SSH connection itself (`x/crypto/ssh`), requests a PTY and starts a shell. Two pump goroutines read stdout/stderr and send binary WebSocket frames; a writer goroutine forwards keystrokes. The **PTY output stream lives here**. This is where session recording taps in (`termAudit.output/input/resize`). `userRecordingLevel(userID)` decides per session: `session_recording` is the master switch, `users.recording_level` (`none` / `metadata` / `input`) overrides the type, and an empty level follows `session_recording_input`; the resolved level is written to the `terminal.open`/`desktop.open` audit entry.
- **Files**: `files.go` (list, download, ZIP, streamed multipart upload, mkdir, rename, delete) over a small pool of SFTP clients (`sftp_pool.go`) or FTP/FTPS; `search.go` (name and content search); `conntest.go` (test a connection).
- **Host keys**: `hostkeys.go` verifies SSH host keys (trust on first use or strict) and pins FTPS certificates (`known_hosts` table).
- **Dialing and jump hosts** (`jump.go`): every SSH/SFTP operation (terminal, SFTP pool, search, transfer, connection test, tunnels) gets its client from `dialSSH(c, onNewKey)`. When `connections.jump_conn_id` is set, `jumpChain` resolves the chain (same owner, SSH only, at most 5 hops, no loops), the first hop is dialed with `ssh.Dial`, each further hop with `prev.Dial("tcp", host)` (a `direct-tcpip` channel) plus `ssh.NewClientConn`. Each hop uses its own credentials and host key check. When the target client closes, the hops close too. FTP/FTPS behind a jump host use `ftp.DialWithDialFunc` with the last hop's `Dial`. `validateJump` checks a choice when a connection is saved. A hop with a proxy (`connections.proxy_id`) is reached through it: `proxyOf` resolves the proxy (access, login, vault credential), `resolvedProxy.dial` opens the TCP connection to the proxy (directly or with the previous hop's `Dial`) and performs the SOCKS / HTTP CONNECT handshake, and `sshOverConn` runs the SSH handshake on that connection. `jumpPath` describes the route with the proxies (`bastion → socks5://10.1.1.1:1080`).
- **Proxies** (`proxy.go`): tables `proxies` (owner, kind `socks5` / `socks4` / `http` / `wrm_tunnel`, host, port, user name, encrypted password or `credential_id`, `remote_dns`, `tunnel_id`, `shared_all`) and `proxy_grants`. Own SOCKS5 (RFC 1928 / 1929), SOCKS4 / 4a and HTTP CONNECT (Basic) clients return `proxyError`s that tell proxy and target apart (unreachable, authentication, SOCKS reply codes, HTTP status). Non-SSH paths use `openTargetRoute(c)`: the last jump host's SSH client (if any) plus c's proxy, with a `Dial` for FTP (`DialWithDialFunc`), Redfish (`http.Transport.DialContext`), status probes, the connection test and the ephemeral local relays of web interfaces and remote desktops (`tunnelRun.useRoute`). `wrm_tunnel` proxies start the referenced dynamic tunnel through `tunnelMgr.start(…, "proxy")` (idle stop after 30 minutes) and talk SOCKS5 to its listener. A shared proxy with a password is refused behind the grantee's own jump hosts; IPMI / SOL with a proxy are refused (UDP). `inContainer` (`/.dockerenv`, `/run/.containerenv`) adds the `docker_loopback` warning for 127.0.0.1 proxies. Policy `proxies`.
- **Folder defaults**: `folders.jump_conn_id` / `folders.proxy_id`. `connections.jump_conn_id` / `proxy_id` store the choice (NULL = as the folder, -1 = none, > 0 = this one; earlier binaries read NULL and -1 as none). `loadConnectionRaw` / `loadUserConnections` apply the folder defaults (`applyFolderDefaults`, `resolveRouteDefaults`): `Connection.JumpID` / `ProxyID` are the **effective** route everywhere on the server, the stored choice stays in `jumpRaw` / `proxyRaw` (API `jump_choice` / `proxy_choice`, export). SQL that needs the effective route (live status) uses `effJumpSQL` / `effProxySQL` with `folderJoin`. A jump host does not inherit itself; loops through folder defaults are refused on save (`validateRoute`).
- **Tunnels** (`tunnels.go`): definitions in `connection_tunnels` (kind `local` / `remote` / `dynamic`, listen host:port, target host:port, open scheme/path, start mode `manual` / `connect` / `always`). The `tunnelManager` keeps running tunnels by key (`t<id>`, or `w<conn>u<user>` for temporary web tunnels). A running tunnel has its own SSH client (via `dialSSH`), a listener (local: `net.Listen` on the WRM machine → `client.Dial`; dynamic: a small SOCKS5 server (CONNECT, no auth) → `client.Dial`; remote: `client.Listen` (`tcpip-forward`) → `net.Dial` on the WRM side), per-tunnel counters, a 30 s keepalive and automatic reconnect with backoff while the listener stays open. `connect` tunnels are reference-counted by the terminals of the connection (`holdConn` / `releaseConn` with a grace period); `always` tunnels start after the database at boot. Changes are pushed to the owner's browsers through `/ws/events` (`tunnels_changed`). Policies are checked when a tunnel is saved, started, and again when a policy changes (`applyPolicy`).
- **Remote desktop** (`guac.go`): RDP, VNC and Telnet go through guacd. `/ws/desktop` authorizes the connection like a terminal, opens a temporary tunnel through the jump hosts when needed, connects to `guacd_address`, performs the handshake (`select` → `args` → `size`/`audio`/`video`/`image`/`timezone`/`connect` → `ready`) with the stored parameters (`connections.options`, JSON) and then relays complete instructions: guacd → browser in batches (recorded to `recordings/…/<uid>.guac.gz`), browser → guacd only allow-listed opcodes. Sessions use `terminal_sessions` (`protocol` rdp/vnc/telnet) and `session_recordings` (`format` `guacamole+gzip`); the browser replays them with `Guacamole.SessionRecording`. Replay shows the wall-clock time at the playhead (`replay.startMs` from `started_at` plus the position) next to the offset for both formats, and the asciicast header already carries the Unix `timestamp` the player adds to, so a recording made by an older build still shows exact times.
- **Terminal backends** (`console.go`): the terminal WebSocket talks to a `termIO` (stdin, stdout, start, resize, wait, keepalive, close): an SSH shell, the serial console over the BMC's SSH (the console command is typed once the BMC prompt is quiet), IPMI Serial-over-LAN (`ipmitool sol activate` on the last jump host — the password goes over stdin after the wrapper turned echo off — or locally in a pseudo terminal, `tty_linux.go`), or a serial port of the WRM server (raw termios, `tty_linux.go`).
- **Out-of-band management** (`bmc.go`): `connections.bmc` holds a JSON BMC setting. Redfish requests use an `http.Transport` whose `DialContext` goes through the last jump hop when needed and whose TLS check pins self-signed certificates (`pinnedTLSConfig`, shared with FTPS, stored in `known_hosts` as `bmc://host:port`). IPMI runs `ipmitool` with `-E`, locally or on the last hop. Power actions map to Redfish `ResetType`s / `ipmitool chassis power`.
- **Quick connect & notes** (`quick.go`): a quick connection is an ordinary row in `connections` with `temp_until` set (RFC 3339, 24 hours after the last use). It goes through `normalizeConnection`, `validateJump` and `checkAuthRefs` like a saved one, is created with `monitor=0`, is excluded from export, and `touchQuick` moves `temp_until` whenever a terminal or desktop opens it. `runQuickCleanup` deletes expired rows every 10 minutes unless a terminal of the connection is open; `PUT … {temporary: false}` clears `temp_until`. `connections.notes` holds the owner's notes; lists only return `has_notes`, `GET /api/connections/{id}` returns the text, the browser renders a small markdown after escaping everything.
- **Network tools** (`nettools.go`): `POST /api/nettools` validates the target (host name / address characters only), takes a per-user lock and runs the tool either on the WRM server (`net.Dial`, `exec.CommandContext` with arguments, no shell, `net.Resolver`, `http.Client`) or from a source connection of the user through `dialSSH`: port and HTTP checks use `client.Dial` (`direct-tcpip`) so nothing runs on the server, ping / traceroute / DNS run a fixed POSIX script with the shell-quoted target (`runRemoteScript`). The HTTP check does not follow redirects and verifies the certificate separately against the system roots to report trust without failing.
- **Installable app** (`pwa.go`): `/manifest.webmanifest` and `/sw.js`. The service worker cache is named after `AppVersion` (`wrm-<version>`), precaches the vendor scripts and brand files, serves `/static/` cache-first, never touches `/api/` or WebSockets, and falls back to an offline page for navigations when the server is unreachable.
- **Tags & inventory** (`inventory.go`): `connections.tags` holds normalised, comma-joined tags. CSV files are decoded (UTF-8 / UTF-16 / Windows-1250) and split with `encoding/csv` after separator detection; `.xlsx` workbooks are read with `archive/zip` and `encoding/xml` (workbook, relationships, shared strings, sheet). Rows become `importItem`s through a field → column mapping and go through the same `importer.commit` as the mRemoteNG / OpenSSH imports. NetBox objects are fetched page by page (`/api/dcim/devices/`, `/api/virtualization/virtual-machines/`), get `ext_id` `netbox:<host>:<kind>:<id>` and `ext_tags` (the tags NetBox controls), so a later import updates them instead of duplicating; `inventory_sources` keeps the address and the encrypted token per user.
- **SSH key store** (`keys.go`): table `ssh_keys` (owner, type, public line, encrypted private key, fingerprint) and `ssh_key_deployments` (key ↔ connection). Connections with `auth_method` `KEY_REF` point to a key (`connections.key_id`). Deploy / revoke / "who has access" log in with `dialSSH` and run small POSIX `sh` + `awk` scripts (`runRemoteScript`) that read the key or its base64 blob from stdin and change `~/.ssh/authorized_keys` in place.
- **Credentials vault** (`credentials.go`): tables `credentials` (owner, user name, encrypted password and pending password, optional `key_id`, host patterns, `shared_all`, rotation interval and status) and `credential_grants`. Connections with `auth_method` `CREDENTIAL` point to one (`connections.credential_id`). `loadConnection` calls `resolveConnectionAuth`, which replaces `KEY_REF` / `CREDENTIAL` by `KEY` / `PASSWORD` with the decrypted secret after checking ownership, grants and host patterns (for grantees also the jump hosts); `dialSSH` resolves every hop the same way, and a failure is kept in `authErr` and reported at login. Rotation (`startRotation` / `runRotation`) runs in the background: pre-flight logins, `passwd` over a PTY per user@host, verification, rollback; the browser polls `/api/credentials/{id}/rotation`.
- **Snippets** (`snippets.go`): table `snippets` (owner, scope all/folder/connection, `auto_run`, `shared`). Variables are expanded per terminal (browser for manual use, server for run on connect). `ssh_ws.go` types run-on-connect snippets into stdin once the first output has been quiet for 400 ms (at most 5 s after the shell started).
- **Folder bookmarks** (`bookmarks.go`): table `bookmarks` (owner, name, path, scope global/folder/tag/connection, `start_dir`, `shared`, sort). The server expands the path variables (`{host}`, `{name}`, `{user}`, `$USER`) per connection and builds the shell-quoted `cd -- '<path>'` (a leading `~/` stays unquoted); the browser never builds the command. The start directory bookmark (most specific scope) is typed by `ssh_ws.go` before the run-on-connect snippets, and the file manager opens there; `files.go` resolves `~/…` against the SFTP home / FTP login directory. Share participants get only the owner's shared global bookmarks.
- **Broadcast input** is done by the browser (`termInput` sends the same keystrokes to every terminal of the group); each terminal WebSocket receives a `broadcast` control message so the server can audit it per terminal session and refuse it when `broadcast_enabled` is off.
- **Live status** (`status.go`): `statusMonitor.round()` loads all monitored connections (effective route), builds one target per host:port (per proxy and host:port with a proxy, or per jump host and host:port when `status_jump_checks` is on), probes them with 32 workers (TCP connect, SSH/FTP greeting, one retry), keeps state and "since" per target, derives the state of connections behind jump hosts from the jump host, and sends `status_changed` to owners whose connections changed. Transitions to down (from up, or from unknown behind a jump host) and from down back to up are passed to `notifyStatusChange` for the owner.
- **Git workspace** (`git.go`, `git_source.go`, `git_bundle.go`, `git_scan.go`, `git_monitor.go`; UI in `static/git.js`, loaded by `openGit()` on first use): everything is per user. `git_sources` (GitLab / GitHub / Gitea with an encrypted token, or an imported bundle whose `bundle.json` is kept in `info`), `git_trees` (path → blob ID per source, project and commit; immutable, cached forever), `git_blobs` (per source and blob ID: normalised SHA-256 with CRLF → LF, the hash with every CR removed, size and content up to 8 MB; bundle payloads use `sha256:<hash>` as blob ID), `git_workspace` (catalog JSON, settings, last check), `git_targets` (resolved ref and files with per-file history per service) and `git_installs` (server, path, environment, state and the last comparison as JSON). `gitProvider` talks to GitLab API v4 / GitHub REST / Gitea API v1 (pinned TLS for self-signed servers, no redirects to other hosts); `computeTarget` resolves the ref (branch-aware tags from the branch's last 500 commits, numeric version sort, fallback branches), lists the trees of the target and the earlier tags, fetches only unknown blobs and builds the history; it also keeps the resolved version list and each file's oldest version, so `detectInstallVersion` can name the deployed version from the code alone (an exact old version, or *Mixed / modified* when no single version matches) and `VERSION.md` is only read when the UI asks for it. `checkServer` logs in once per server (`dialSSH`), runs a `find` over the roots for the fingerprint files (`discoverOn`) and a hashing script (`scanOn`: `tr -d '\r' < f | sha256sum`, `VERSION.md`, `grep` of systemd / supervisor unit files), and `compareInstall` derives the file and installation states. `runGitMonitor` checks users with periodic checks on every `git_check_interval_minutes` and passes new versions, drift and unreachable servers to `notifyUser` (events `git.new_version`, `git.drift`, `git.unreachable`). API: `/api/git`.
- **Git files and check jobs** (`git_files.go`, `git_jobs.go`): `listInstallFiles` runs one `find` over an installation (`listOn`: prunes plus the catalog's `ignore_dirs`, `stat -c` / `stat -f`, the check's hash, symlinks with `readlink`, unreadable files and directories, at most 10 000 entries) and joins it with the repository at the target (`openRepoView`: the target's files plus the cached tree of `commit_full` below the subdirectory); `catalogReason` names why a file is (not) compared and `trackedState` (shared with `compareInstall`) gives tracked states. Untracked repository files are compared through `git_blobs` (`ensureBlobs`, at most 200 per listing) and never affect the installation state. `readServerFile` reads one file with `cd` + `pwd -P` (no path out of the installation, no symlink) for `viewInstallFile` and `installDiff` (any repository file except protected ones). `installCommits` uses `gitProvider.compareCommits` (GitLab `repository/compare`, GitHub `compare/a...b`). A check job (`gitCheckJob`, in memory, one per user under `gitLock`) resolves installations, servers, stale or never-checked selections (`planGitJob`), logs in once per server, optionally discovers, then scans every installation on its own session (`scanOn`) bounded by `git_check_per_server` and `git_check_parallel`, saving each result at once (`saveInstallResult`; `saveInstallError` keeps the last good files, `git_installs.last_ok_at` / `last_ok_state`). The browser polls `GET /api/git/check/jobs/current?since=<seq>` and gets the installations finished since; cancel closes the job's SSH clients so running scans are dropped unsaved.
- **Git runs** (`git_runs.go`, `git_deploy.go`): `git_runs` holds every run (kind update / upgrade / rollback / stamp / restart, state, the request with the **pinned targets**, the per-installation results, scheduled / started / ended times, the notice time) and `git_pending_restarts` the installations updated without a restart. `createGitRun` validates the request (policy per kind, ownership, the typed server name for production installations, restart choice, schedule), pins the targets (`upgradeTarget` computes a target at another ref, cached for 30 minutes between plan and run), stores it and either starts it (`startGitRun`: one running run per user, progress in memory in `gitLive`) or leaves it *scheduled*; a restart at a time or after a delay is a child run waiting for its parent (`releaseChildRestarts`). `executeGitRun` works on the installations in order and stops at the first failure. Per installation (`deploySession`, one SSH login): `scanOn` + `planFiles` + `selectRunFiles` (fresh comparison, default old + missing, ticked local changes only), `prepare` (host, user, owner, tools, line endings, Python import lines via `awk`), `danglingImports`, `makeBackup` (`mkdir` claims `<install>/.deploy-bak/<id>-<time>`), `stage` (temporary file per file, copied from the old one, content on stdin, verified with the `tr -d '\r' | sha256sum` hash), `commit` (renames, deletes), `checks`, `restore` on failure, `versionMD` / `pyJSONLine` + `appendUpdateLog`, then `refreshInstallState`. `restartUnits` restarts and health-checks units. `runGitScheduler` marks runs interrupted by a stop, then every 20 s (`gitSchedulerTick`) starts due runs, skips runs older than `git_schedule_grace_minutes` and sends `git.job_upcoming` 15 minutes before. Events `git.deploy_started`, `git.deploy_done`, `git.deploy_failed`, `git.restart_scheduled`, `git.restart_done`; audit `git.update`, `git.upgrade`, `git.rollback`, `git.restart`, `git.stamp`, `git.run_scheduled`, `git.run_cancelled`, `git.run_skipped`.
- **Git install and transfer** (`git_provision.go`, `git_template.go`): runs of kind *install* / *transfer* (policies `git_install`, `git_transfer`; never scheduled; restart choice none / now). `createProvisionRun` validates the request (`validInstallDir`, the per-host file choices against the pinned target, the unit, the typed server name for production targets and overwrites), stores it **redacted** (`redactedProvision`: no typed values or contents, vault references only) and starts it with the full request in memory. `gitPrepare` (`POST /api/git/provision/prepare`) resolves the targets (`installTarget`: the stored target, a bundle, or another ref via `upgradeTarget`), the per-host slots (`installSlots`: templates by name — `templateDest` — with their fields from `templateFields`, protected files of the repository, literal protected names and the protected files of other installations) and runs `precheckDirs` (one script: exists / files / `VERSION.md`, nearest existing parent, writable, `df -Pk`, owner, `python3` / `node` / `tar`). Install: contents from `gitFileContent` plus the filled files (`fillTemplate`, `vaultValue` with the credential's host list, `readInstallFile` over SSH) are packed with `tarOf`; transfer: `listForTransfer` (hash and size per file) and `transferSelection` / `transferExcluded`, then `runRemotePipe` streams `tar -c` on the source into the target. Both unpack with `receiveScript` into `<dir>/.wrm-incoming-<run>` and verify the hashes (`verifyStaged`); `placeStaged` backs up replaced files (`makeBackup`), creates directories, renames (`commit`), runs the checks and rolls back (`restore`) on failure. Then `VERSION.md` (`versionMD`, or `retargetVersionMD` for a transfer), the `updates.jsonl` line, `register` (a `git_installs` row added by hand, `createUnit` for the optional systemd unit / supervisor program as root or with `sudo -n`, `refreshInstallState`); a start uses the restart step of the runs. Audit `git.install`, `git.transfer`.
- **Git .gitignore helper** (`git_gitignore.go`, the *.gitignore* tab of `static/git.js`): `gitIgnoreState` gathers per service the *extra* files of the stored comparisons (`extraCandidates`, sizes from `scanOn`'s `wc -c`, `suggestIgnorePattern`), reads the head of the service's branch (`readRepo`: `branchCommits`, the cached `tree`, the `.gitignore` blob), detects stacks (`detectStacks`) and secret / protected files (`gitIgnoreWarnings`, template names like `templateDest` reads them). `mergeGitignore` appends new patterns only (line endings kept); preview diffs with `unifiedDiff`; the download is the default. `createGitignoreMR` uses the source's **write token** (`git_sources.write_token`, `newGitWriteProvider`, `gitProvider.send`): GitLab `repository/branches` + `repository/commits` + `merge_requests`, GitHub `git/refs` + `contents` (with the blob SHA when the file exists) + `pulls`. Policy `git_gitignore_mr`, the typed project checked by the server, audit `git.gitignore_mr`.
- **Git environments** (`git_env.go`, `git_env_run.go`, the *Environments* tab of `static/git.js`): `gitCatalogApp.Environments` (ordered destinations `{server, path}` resolved by connection name with `envConn`, `confirm`, `allowed_refs` via `refAllowed`, `ignore`, `post_deploy`, `keep_backups`, `state_dir`), validated in `normalizeEnvs` and `checkEnvPaths` (nested app paths unless excluded, state directories inside app paths). `envPlanRequest` resolves the target (`installTarget`), checks `allowed_refs` and computes a `gitEnvDestPlan` per destination (`envPlanCtx.destPlan`: one `envScanScript` per destination — CR-stripped hash, CR count, symlinks, unreadable files, `VERSION.md`, `state.json`, the lock — classified as new / changed / eol / same / removed (in the tree of the deployed commit, `previousTree`) / extra / protected / ignored, type conflicts, warnings, `fingerprint`); plans are kept in memory (`gitEnvPlans`, 2 hours) and used once (`takeEnvPlan`). Runs: `createGitRun` hands requests with `env` to `createEnvRun` (typed environment name, `post_deploy` pinned, plan used once, exclusions remembered in `git_env_exclusions`); `executeGitRun` calls `envDeployItem` / `envRollbackItem`. A deploy item: `envLock` (mkdir `<state>/.lock` + owner file, server time) → `destPlan` again and the fingerprint compare → `envSelection` → `envProbe` → `tarOf` + `receiveScript` (`gitTransferTimeout` ≥ 1 h; `envPartial` records an interrupted transfer) → `verifyStaged` → `envBackup` → `envCommit` (stdin lists: deletes with removed directories, then renames keeping mode / owner) → `envChecks` → manifest `deploys/<id>.json` and `state.json` (`envWriteFile`), `updates.jsonl`, optional `post_deploy`, `envAppendHistory`, `envPrune`, `envRegister` (a `git_installs` row) → `envUnlock` (own id only). A rollback item checks `state.json` / the manifest / the backup under the lock and runs `envRollbackScript` (added files and current versions moved to `backups/rollback-<id>/`, removed directories re-created, symlinks skipped, `DRY=1` for dry runs). `envBreakStale` removes a stale lock (max(30 min, transfer timeout)) after checking it again on the server. `envCell` (lazy overview cells, code-based detected version, commits behind via `compareCommits`, drift), `envHistory` and `envDoctor` read the destinations in parallel (`forEachDest`). ## Stored connections and credentials

- `connections` (host, port in `host`, username, auth method, `password`, `private_key`, `key_path`, `key_id`, `credential_id`, folder, owner `user_id`, `jump_conn_id`, `web_path`, `tags`, `ext_id` / `ext_tags` for inventory sync), `connection_tunnels` and `folders`. This is the "servers" inventory of the plan. Keys of the key store (`ssh_keys`) and vault credentials (`credentials`, `credential_grants`) are shared by many connections.
- Passwords, private keys and TOTP secrets are encrypted with **AES-256-GCM** before they are stored (`security.go`). The key comes from `ENCRYPTION_KEY`, `ENCRYPTION_KEY_FILE` or a random key file `<DB_PATH>.key` (mode `0600`), never from the database or git.
- Secrets are never returned by the API: the UI only "sets/replaces" them. They are decrypted in memory when connecting. The only exceptions are explicit, audited owner actions after re-authentication (config export with secrets, private key export, *Show* of a vault password), all behind the `allow_secret_export` policy.
- Server-side key files (`key_path`, `~/.ssh`) are limited to administrators by default.

## Canvas and collaboration

- The multi-window canvas (windows, tabs, snapping) is **client-side state**. Saved workspaces are stored on the server (`sessions` table, `/api/sessions`).
- **Sharing** (`shares.go`): `share_links`, `share_items` (connections/folders), `share_members` and `share_participants`. Five roles (observer, viewer, operator, moderator, owner) with permissions, enforced on every request by `authorizeConnection(r, connID, perm)`.
- **Realtime** (`collab.go`): `/ws/share/{token}` rooms. The server is the authority for identities, roles, presence, chat, terminal sharing (the sharer's browser streams output to watchers), keyboard control grants and voice signalling. `/ws/events` carries per-user notifications.

- **Migrations** run at startup in `initDB` (`main.go`), and they are idempotent: `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE … ADD COLUMN`, indexes and triggers. `ensureTable` keeps a table left by an earlier build with an incompatible layout as `<name>_old_<time>` and creates it again.
- Migrations are **additive only**: new tables, columns, indexes and triggers, and no data is removed or rewritten. A previous binary ignores the new objects, so a downgrade is "run the previous binary". This is the reversible ("down") path, and it loses no data.

### Decisions where the plan's example names collide with existing code

- **`terminal_sessions`** instead of `sessions`, because `sessions` already stores saved workspaces.
- **`/api/recordings`** instead of `/api/sessions`, because `/api/sessions` is the workspace API.
- The plan's `servers` are the existing **`connections`** (each with an owner). Phase 2 adds grants on top of them.
- `audit_log` keeps its existing column names (`action` = the plan's `event_type`, `details` = `detail_json`, `ip` = `client_ip`) and gains `conn_id` (server), `session_id`, `prev_hash` and `hash`.
- Recordings are **gzip-compressed asciicast v2** files on disk (`WRM_RECORDINGS_DIR`, default `recordings/` next to the database). The checksum is the SHA-256 of the stored file. The API serves the plain `.cast`.

## Medium deploy-config from Git, build user and default engine (v12.9.1)

`medium_config_git.go` keeps WRM's own Git copy of deploy-config in `<DB>.medium/users/<id>/native-config` with `.wrm-git.json` (`mdGitConfigState`: source, project, branch, commit, Git blob id and SHA-256 of every pulled file). `mdConfigDir` prefers that copy when the state file exists, then a pending imported config, then the imported one. `mdConfigRepoSource` maps the user's `DEPLOY_CONFIG_REPO` to a WRM Git source with `mdFindSource`. **Pull** (`mdGitConfigPull`) reads the branch head's tree and the deploy-config files through the read provider, writes them into a temporary directory next to the copy, loads it with `mdLoadConfig` and swaps the directories; local changes (`mdLocalConfigChanges`, by SHA-256 against the pulled content) make it `409` unless discarded. **Push** (`mdGitConfigPush`) validates the copy, re-reads the branch head and refuses when a changed file's blob id moved, then `mdGitCommitFiles` writes one commit with the write provider: GitLab `POST /repository/commits` with actions, GitHub `git/commits` → `git/trees` (with `base_tree`) → `git/commits` → `PATCH git/refs/heads/<branch>` with `force: false`, Gitea `POST /contents` with file operations; the result is pulled back with discard. Routes: `GET /config/git`, `POST /config/git/{pull,push,stop}`; activity ops `config_pull`, `config_push`.

`medium_build_user_unix.go` resolves `medium_build_user` (`mdResolveBuildUser`: root needed to switch accounts, no uid or gid 0, `mdAccountCanRead` by permission bits on the database, key and Medium root) and `mdApplyBuildUser` chowns the build directory, sets `SysProcAttr.Credential` with the supplementary groups and a minimal environment; the build directory is `work/` inside a root-owned `0711` directory, `mdReadBuildOutput` Lstats every component of `source_dir`, and `mdReclaimBuildDir` chowns it back (each directory before WalkDir lists it), drops group/other write and refuses foreign hard links; Windows has a stub that refuses a set value. `mdBuildOutcome.User` and `mdPlanResult.BuildUser` carry it to the plan. `mdProjectEngine` returns the stored choice (`native` or `docker`) or `mdDefaultEngine` (`medium_default_engine=native` and `mdNativeAllowed`); `mdMigrateDefaultEngine` runs at start and stores `original` once when the setting was never stored and the original tool's directory exists. The Medium status carries `default_engine`, and the UI moves the WRM engine card first and folds the original tool's card (`mediumArrange`).

## Medium screens: file details, line endings, deploy-config editor (v12.9.0)

`medium_screens.go` adds three pieces on top of the native plan. **File details** (`GET …/plan/<id>/diff`) look up a change of the user's own finished run, read the branch side from the run's prepared tree and the server side over the linked connection (Lstat first, so a link or directory is reported instead of followed), and compare them with the Git workspace's `unifiedDiff`. **Line endings:** `mdMarkEOL` runs inside `mdPlanServer` and sets `mdChange.EOL` when the content without `\r` equals the source's; `mdSFTP.HashesNoCR` hashes on the server in one `xargs -0 sh -c` call with stdin-fed names, and any other destination (or a server without `sha256sum`) is read over SFTP. The marking never changes the plan or its revision; `mdHistoryEOL` adds `counts.eol` to the history entry from the reviewed plan. **deploy-config editor:** names match `servers.yaml`, `environments.yaml` or `projects/<name>.ya?ml`; a save copies the configuration into a temporary directory with the edit, loads it with `mdLoadConfig`, checks the base hash under a mutex and replaces the file through a temporary file in the same directory. CRLF files stay CRLF.

## Medium native engine: deployments and rollbacks (v12.7.0)

`medium_state.go` holds the server-side records in the original tool's format: `mdRecord` (`current.json`) and `mdHistoryEntry` (one `history.jsonl` line; the record's fields first, then `action`, `server`, `note`, `rolled_back`, `current`, `previous`, the path lists and `counts`), written by `mdMarshalLine` as compact JSON without HTML escaping with every field present, and `mdLockOwner`. `mdChooseRollback` reproduces the original's choice: `mdAppliedDeploys` stacks the entries that changed files (`counts` present, or an old note that does not mark a failure before the transfer) and removes the ones a complete rollback named; the top is undone and restores its `previous` record when the entry has that key, otherwise the next entry below it that set `current.json`. `medium_host.go` extends `mdRemote` with writes (`mdHost`): `mdSFTP` uses SFTP (`posix-rename` with an `mv` fallback for another file system, `Symlink` checked by `ReadLink` with an `ln -s` fallback) and `sh -c` over a new SSH session for the scripts (`Sh`, every path through `shellQuote`, JSON through stdin) and the account's login shell for `post_deploy` (`Login`); tests use `mdLocal`.

`medium_deploy.go` runs a job (`mdJob`, one per user in `mdJobs`, kept for an hour, an activity row and an audit entry when it ends). `mdDeployOne` per destination: `mdAcquireLock` (`mkdir lock` then `owner.json`; exit 75 = held, with the owner), `mdPlanOn` again under the lock and `mdPlanDifference` against the reviewed plan's change keys, then the manifests (`<id>.added`, `<id>.dirs` with mode, uid, gid), removals deepest first into `backups/<id>/`, `mkdir` shallowest first, uploads to `.<base>.wrm<6 hex>` beside the target (`WriteNew` with `O_EXCL`, four in parallel, mode from the source's executable bit minus the server's umask or the server file's own mode), `sha256sum` of the temporary files, the commit (old file to the backup, then rename), `post_deploy`, `mdVerify`, `mdWriteState` (current.json by temporary file and rename, a history line appended) and `mdPruneBackups`; the lock is released in a `defer` with the owner check (`grep -F '"deploy_id":"<id>"'`). An error after the first change writes a partial entry (`current: false`). The plan revision (`mdPlanRevision`, SHA-256 over commit, exclusions and server plans) binds a deployment to what was reviewed; a run is deployed once (`mdRun.used`). Exclusions are literal rules (`mdExactRule`) added to the project's ignore rules. `medium_rollback.go` reads the manifests through `mdCheckedRel` (relative, no `..`), refuses symlinks on the way (`mdLinkOnPath`), moves the deployment's files to `rollback-<rid>/`, restores the backup and the recorded directory modes, and writes a `ROLLBACK` entry. `medium_deploy_api.go` adds the per-user engine choice (`medium_project_engine`) and the routes; `mdCancelUserJobs` is called from `endUserAccess` and the lockdown. Tests compare a native deployment with real `rsync --backup` and roll it back to the starting tree.

## Medium native engine preview (v12.6.0)

`medium_config.go` reads `deploy-config` through `yaml.v3` nodes (ordered keys, duplicate-key errors, `<<` merges, YAML 1.1 booleans) into `mdConfig` and validates it with the original tool's rules, including global checks of overlapping destinations and state locations. `medium_filter.go` compiles rsync exclude patterns (directory-only, anchored, `*`/`**`/`***`, POSIX classes) and `fnmatch` for `allowed_refs`. `medium_engine.go` walks a destination through the `mdRemote` interface (`mdSFTP` in production, `mdLocal` in tests), hashes candidates with `sha256sum` on the server (SFTP reads as fallback) and computes `mdDiff`, the changes `rsync -rlc --delete --exclude` would make; tests compare it with real rsync on fixed and random trees. Server state is read from `current.json`, the tail of `history.jsonl` and `lock/owner.json` at the original paths. `medium_native.go` finds the WRM Git source for a project's repository (host and path), resolves refs, builds the source tree from the cached Git tree and blobs, maps servers to saved SSH connections (`medium_server_links`, automatic match by address and user) and runs one background preview per user. With *Compare*, it asks the running original tool for its plan through `POST /__wrm_plan` in `medium_wrapper.py` (bridge key required) and diffs both plans on the original's prepared source. The preview is read-only: it opens SFTP sessions and runs only `sha256sum` on destinations.

## Claude Desktop extension and Claude Code plugin (v12.5.1)

`mcp_bundle.go` serves `POST /api/mcp/claude-desktop`: an MCP bundle (`wrm-pro.mcpb`, a zip with `manifest.json` version 0.2, `server/index.js` and `icon.png`) for Claude Desktop, which starts only local stdio servers and whose custom connectors connect from Anthropic's cloud. The bundle's server is `mcpb/server/index.js` (embedded with `go:embed`), a dependency-free Node.js port of `runMCPStdio` that Claude Desktop runs with its built-in Node.js: it forwards newline-delimited JSON-RPC to `/mcp` with the bearer token, the initialize request first and the rest concurrently, copies event streams (approval elicitations) to stdout as they arrive, keeps `Mcp-Session-Id` / `MCP-Protocol-Version`, sends DELETE at the end, and turns transport or HTTP errors into JSON-RPC errors. The manifest's `user_config` carries the WRM address (default: `mcpBaseURL`), the token (sensitive; default only when the wizard passes a `wrm_pat_…` token) and an optional CA file; these reach the bridge as `WRM_MCP_URL`, `WRM_MCP_TOKEN`, `WRM_MCP_CA_FILE`. The endpoint needs a WRM sign-in and `mcpUserAllowed`, accepts only a well-formed `wrm_pat_` token and audits `mcp.desktop_extension` (`with_token`, never the token). The live view in `static/mcp.js` (`watch`) follows an MCP session's events over `/api/ai/sessions/{id}/events` (the same stream as the assistant panel) and opens once per new session seen in `/api/mcp/active` unless turned off (`localStorage` `wrm_mcp_watch`); its Approve / Deny buttons use the normal approval API. The live view's boxes live in one panel (`#mcp-watch`, `dockPlace`) inside `#rp-ai`, the AI panel of the page layout (`static/layout.js`, available while `wrmMCP.dockAvailable()`); its title bar buttons call `wrmLayout.moveTo` / `hide` / `show`, and `dockStyle` follows the place (row of sessions at the bottom). Below 760 px it sits on `document.body` as a bottom sheet. It is display only: approvals and their cards (`#mcp-cards`) do not depend on it. A denied or timed-out approval returns a tool result that names where it was refused and tells the model to ask the user before trying again. The repository root is also a Claude Code plugin marketplace (`.claude-plugin/marketplace.json`) with one plugin, `packaging/claude-plugin/wrm-pro`, which declares an HTTP MCP server whose URL and `Authorization` header come from the plugin's `userConfig` (the token is `sensitive`, kept in Claude Code's secure storage).

## Monitoring, client GitLab and MCP workflows (v12.4.4)

`monitoring.go` owns additive encrypted per-connection profiles and bounded samples, four background workers, manual polls/history/detection and transition notifications. `monitoring_zabbix.go` handles passive JSON/legacy frames, bounded zlib, SSH/network routes, verified certificate TLS, existing remote PSK helper and HTTPS `item.get`. `monitoring_logs.go` supplies bounded SFTP root discovery, symlink-component checks, timestamp/timezone filtering, tail signatures and segmented search cursors. `static/monitoring.js` owns the overview, embedded Git Functionality and cancelable floating log views; it opens on demand. This is a host metrics/log workspace, not a Zabbix server or hypervisor controller.

Logs (v13.5.0): `log_settings.go` keeps per-connection log settings (table `log_settings`, encrypted JSON; falls back to the Zabbix profile's roots) and the path patterns that label operator and service. `log_discovery.go` discovers over SSH: `logMetaScript` (systemd units and unit files, Supervisor, Docker) and a `find` over the scan paths, every path shell-quoted and taken from the settings or that metadata, never from the request; it falls back to the SFTP walk of `monitoring_discovery.go`. `log_grep.go` serves `logs/grep` (grep over discovered files on the server, hits with a parsed time, ranges and time zones) and `logs/lines` (`tail`, `around` with `sed -n`, `since` with `tail -c +N` or a journal cursor); `logSearchable` is the allow-list both share: only paths and journal units the last discovery returned. `static/logviewer.js` is the viewer (file list, tabs, search, timeline, settings), mounted by `static/monitoring.js`.

Log grouping (v13.6.0): `log_groups.go` decorates every discovered file (`logDecorate`, after SSH discovery and on the SFTP list) with its main folder (`logMainFolders`: `main_folders`, scan paths, Git workspace server roots; longest match), `place` (`logs` or `app`) and an operator group. With `guess_operators`, `logOperatorWords` takes words that occur in two or more service/folder names, at least once not as the first word, and are not products (first word of several names), environment or generic words; `logOperatorGroups` links operators by a common prefix of four or more letters. Explicit operators from patterns and roots are never replaced. Main folders also come before the default label patterns in `newLogLabeler`. The viewer compares services without case and builds the folder tree and Folder filter from `main` client side.

AI chats (v13.5.0): `ai_chats.go` adds `title`, `purpose`, `resumed_from` and `file_path` to `ai_sessions`. A purpose (`logs`, `file`) limits the tools (`aiPurposeTools`, checked in `CallTool` and `toolDefs`) and adds `purposePrompt`; `logs` is always read-only. `search_logs` (`planSearchLogs`) greps the discovered files in one command. After the first answer `autoTitle` asks the model for a title with no tools (`ai_auto_titles`). `resume_from` starts a new session whose history is the earlier chain (`aiResumeHistory`, tool calls flattened to text, 300 KB budget); the events endpoint of a session that is not live answers with one `ended` event (`resumable`). Thinking (`ai_show_thinking`): `aiWithThinking` puts a callback on the context; the Anthropic client then asks for adaptive thinking on the models that support it (`anthropicAdaptiveThinking`) and passes `thinking_delta`, the OpenAI client passes `reasoning_content`; the engine emits `thinking` events and stores the text as transcript kind `thinking`. `static/aichat.js` is the compact chat shared by the log viewer (`openLogAI`) and the file editor; `static/fileeditor.js` is the file manager's editor (Prism layer behind a transparent textarea, find/replace, line diff, conflict check, AI panel).

AI sessions view (v13.8.0): `ai_sessions_view.go` adds `ai_sessions.saved` and `ix_ai_sessions_user`. `GET /api/ai/sessions?view=all` (`aiSessionsViewList`) always filters on the signed-in user, with kind filters (`aiSessionKinds`), a `before` cursor and a `LIKE … ESCAPE` search (`likeEscape`) over the session row and the user, assistant and tool-call transcript rows. `save` sets the flag, which `cleanupAITranscripts` skips while `ai_keep_saved_sessions` is on; `export` writes the stored (already redacted) transcript as Markdown or JSON. Personal AI settings are the `user_ui` key `ai` (`aiPrefsOf`): `aiDefaultProviderFor` uses the personal provider only while `providersFor` still offers it, `aiThinkingWanted` combines `ai_show_thinking` with the user's choice. Resuming an MCP or OpenCode session flattens its tool calls into the earlier context (`aiResumeHistory`). Approvals (`ai_approvals.go`): `requestApproval` keeps the tool call and its plan on the `aiApproval`; with `ai_mcp_later_approval` = `run` a later approval (`resolveVia`) calls `runLater`, which runs a copy of the plan with `Approved` in the background, and a repeated identical call gets that result once (`takeLaterRun`, `laterRunResult`) instead of running again. Elicitation answers: accept → the chosen decision, decline/cancel → `aiViaMCPDeclined` (kept for later); when WRM decides first, the stream sends `notifications/cancelled` for the open elicitation. `Resolve` on an approval that no longer waits returns `aiNotPendingErr` built from the last `decision` transcript row; the API answers `409 {error, decided}` (`aiDecisionError`).

`git_relay.go` adds explicit source cache members, monotonic generation metadata and encrypted API responses. Jobs have an expiring hashed worker key, owner-catalog endpoint allowlist, bounded queues and independent staging. Only successful complete collection publishes in a source/scope-checked transaction; a late older job cannot replace a newer successful generation. The browser or `git_relay_client.go` companion holds its own GitLab token. WRM never receives that token; its repository transport reads a pinned published generation and can request uncached reads from an attached scoped client. Blob identities are checked before use. Native Medium subprocess networking remains separate.

`git_review.go` stores encrypted deduplicated target manifests and hashed, owner/installation/action/ref-bound expiring review tickets. Advanced run creation pins the reviewed target before consulting a later target. Existing environment/Simple fingerprint checks remain. `git_blobs`/`git_trees` preserve immutable deployment content independently from the rotating API response generations.

`mcp_edit.go` changes existing grant scope while retaining bearer hash/expiry and invalidating active MCP/AI sessions and approvals. Session policy signatures and fresh grant checks protect execution after edits. `mcp_prompts.go` and `mcp_picker.go` expose the grant-bound `wrm` prompt and negotiated form/text server selection; newer form enums use titled `oneOf`, older clients retain their enum representation. `ai_inventory.go` supplies structured SFTP read-only inventory without shell classifier bypass. `ai_context.go` applies account/share/path/redaction bounds before previewing selected context. `ai_idle.go` closes quiet provider streams with request cancellation; header and total request deadlines are separately configurable.

`visual_labels.go` stores validated owner-bound folder/connection color/icon choices in an additive table, leaving existing connection/folder schemas readable by older binaries. `terminal_directory.go` starts authorized SSH sessions in a separately quoted POSIX or encoded PowerShell literal directory. The protocol/session/share checks remain in the existing terminal handler.

See [the operation guide](docs/V12.4.4_GUIDE.md) for endpoint lists, bounds and protocol references. Database/key backups must stay paired, including the new encrypted cache/monitoring/review data.

## Appearance and screen lock (v13.7.0)

Themes: every colour, font and radius of the interface is a CSS custom property on `:root` in `static/index.html` (status colours also as `--*-rgb` channels so tints can be written `rgba(var(--red-rgb), .12)`, text variants as `--*-t`). `static/appearance.js` holds the built-in themes, derives the full token set and the xterm palette for the active theme, then applies the user's overrides, the colour-vision palette and the accessibility classes (`ap-symbols`, `ap-focus`, `ap-solid`, …) on `<html>`. Preferences live in `user_ui` under the key `appearance`; a localStorage copy paints the next load early. Addon themes reach it through `wrmAddons.applyThemes()` → `wrmAppearance.setAddonThemes()`; token values that could load or run something (`url(`, `expression`, `;`, braces, angle brackets) are dropped on the client, the server validates the manifest.

Screen lock: `lock.go` keeps `auth_sessions.locked_at` per sign-in session. `requireAuth` calls `screenLockRefuses`, which answers `423 Locked` for a locked session in `screen_lock_mode=server` except for `screenLockAllowedPaths` (me, logout, keepalive, lock, verify, the two preference keys). WebSockets that are already open are not re-checked, so running terminals keep going. `static/lock.js` holds the triggers (idle across tabs via localStorage, hidden, IdleDetector, sleep gap, shortcut), the lock screen, the Settings → Security section, and wraps `initApp` so a page loaded while locked starts the application only after the unlock. A BroadcastChannel locks and unlocks the other tabs of the browser.
