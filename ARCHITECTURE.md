# Architecture

This document describes how Web Remote Manager PRO (WRM) is built. It is the result of
"Step 0 — repo audit" of the extension plan (WRM as a lightweight PAM for teams), and it maps
every phase of that plan to the code that it touches.

## Stack

| Part | What it is |
|---|---|
| Backend | **Go** (version in `remote-manager/go.mod`), standard library `net/http`, no web framework. One self-contained binary. |
| Libraries | `golang.org/x/crypto/ssh` (SSH client), `github.com/pkg/sftp`, `github.com/jlaffaye/ftp`, `github.com/gorilla/websocket`, `github.com/pion/turn/v4` (TURN relay for voice), `modernc.org/sqlite` (pure-Go SQLite, no CGO), `rsc.io/qr` |
| Frontend | One page, `remote-manager/static/index.html`: plain JavaScript, no framework, no build step. `xterm.js` and fonts are vendored in `static/vendor/`. Everything under `static/` is embedded into the binary with `go:embed`. |
| Database | SQLite in WAL mode (`DB_PATH`, default `./remote_manager.db`), mode `0600`. |
| Build / run | `go build`; CI (`.github/workflows/build.yml`) runs gofmt, vet, tests with the race detector, a JS syntax check, cross-compiles 13 targets and publishes releases on tags. `Dockerfile` + `docker-compose.yml` for container deployments. |

## Auth model

- Local accounts in `users` (bcrypt cost 12). The first account is the administrator; self-registration is closed by default.
- Sign-in sessions in `auth_sessions`: a random 256-bit token in the `wrm_session` cookie (HttpOnly, SameSite, Secure over HTTPS). Only the SHA-256 of the token is stored. Sessions expire after idle and absolute timeouts (policies).
- Two-factor authentication: TOTP (RFC 6238) with single-use recovery codes; a policy can require it for admins or everyone (`users.go`, `totp.go`).
- Roles today: `users.is_admin` (administrator or user) plus per-share roles (see Sharing). Policies are in `app_settings` and can be forced with `WRM_<KEY>` environment variables (`settings.go`).
- CSRF: every non-GET `/api` request needs `X-WRM-Request: 1` and a same-origin `Origin`; WebSockets check `Origin` (`security.go`).
- Request bodies are limited per path (`bodyLimitFor`): 1 MB by default, 32 MB for the import endpoints (`/api/config/import*`, `/api/inventory/*`; files up to `maxImportFile` = 20 MB, the same limit the browser checks), streamed uploads by policy. Import handlers answer HTTP 413 with the size and the limit (`decodeImportJSON`).

## SSH / connection layer

- **Terminal**: `GET /ws/ssh?id=…` (`ssh_ws.go`). WRM opens the SSH connection itself (`x/crypto/ssh`), requests a PTY and starts a shell. Two pump goroutines read stdout/stderr and send binary WebSocket frames; a writer goroutine forwards keystrokes. The **PTY output stream lives here**. This is where session recording taps in (`termAudit.output/input/resize`).
- **Files**: `files.go` (list, download, ZIP, streamed multipart upload, mkdir, rename, delete) over a small pool of SFTP clients (`sftp_pool.go`) or FTP/FTPS; `search.go` (name and content search); `conntest.go` (test a connection).
- **Host keys**: `hostkeys.go` verifies SSH host keys (trust on first use or strict) and pins FTPS certificates (`known_hosts` table).
- **Dialing and jump hosts** (`jump.go`): every SSH/SFTP operation (terminal, SFTP pool, search, transfer, connection test, tunnels) gets its client from `dialSSH(c, onNewKey)`. When `connections.jump_conn_id` is set, `jumpChain` resolves the chain (same owner, SSH only, at most 5 hops, no loops), the first hop is dialed with `ssh.Dial`, each further hop with `prev.Dial("tcp", host)` (a `direct-tcpip` channel) plus `ssh.NewClientConn`. Each hop uses its own credentials and host key check. When the target client closes, the hops close too. FTP/FTPS behind a jump host use `ftp.DialWithDialFunc` with the last hop's `Dial`. `validateJump` checks a choice when a connection is saved. A hop with a proxy (`connections.proxy_id`) is reached through it: `proxyOf` resolves the proxy (access, login, vault credential), `resolvedProxy.dial` opens the TCP connection to the proxy (directly or with the previous hop's `Dial`) and performs the SOCKS / HTTP CONNECT handshake, and `sshOverConn` runs the SSH handshake on that connection. `jumpPath` describes the route with the proxies (`bastion → socks5://10.1.1.1:1080`).
- **Proxies** (`proxy.go`): tables `proxies` (owner, kind `socks5` / `socks4` / `http` / `wrm_tunnel`, host, port, user name, encrypted password or `credential_id`, `remote_dns`, `tunnel_id`, `shared_all`) and `proxy_grants`. Own SOCKS5 (RFC 1928 / 1929), SOCKS4 / 4a and HTTP CONNECT (Basic) clients return `proxyError`s that tell proxy and target apart (unreachable, authentication, SOCKS reply codes, HTTP status). Non-SSH paths use `openTargetRoute(c)`: the last jump host's SSH client (if any) plus c's proxy, with a `Dial` for FTP (`DialWithDialFunc`), Redfish (`http.Transport.DialContext`), status probes, the connection test and the ephemeral local relays of web interfaces and remote desktops (`tunnelRun.useRoute`). `wrm_tunnel` proxies start the referenced dynamic tunnel through `tunnelMgr.start(…, "proxy")` (idle stop after 30 minutes) and talk SOCKS5 to its listener. A shared proxy with a password is refused behind the grantee's own jump hosts; IPMI / SOL with a proxy are refused (UDP). `inContainer` (`/.dockerenv`, `/run/.containerenv`) adds the `docker_loopback` warning for 127.0.0.1 proxies. Policy `proxies`.
- **Folder defaults**: `folders.jump_conn_id` / `folders.proxy_id`. `connections.jump_conn_id` / `proxy_id` store the choice (NULL = as the folder, -1 = none, > 0 = this one; earlier binaries read NULL and -1 as none). `loadConnectionRaw` / `loadUserConnections` apply the folder defaults (`applyFolderDefaults`, `resolveRouteDefaults`): `Connection.JumpID` / `ProxyID` are the **effective** route everywhere on the server, the stored choice stays in `jumpRaw` / `proxyRaw` (API `jump_choice` / `proxy_choice`, export). SQL that needs the effective route (live status) uses `effJumpSQL` / `effProxySQL` with `folderJoin`. A jump host does not inherit itself; loops through folder defaults are refused on save (`validateRoute`).
- **Tunnels** (`tunnels.go`): definitions in `connection_tunnels` (kind `local` / `remote` / `dynamic`, listen host:port, target host:port, open scheme/path, start mode `manual` / `connect` / `always`). The `tunnelManager` keeps running tunnels by key (`t<id>`, or `w<conn>u<user>` for temporary web tunnels). A running tunnel has its own SSH client (via `dialSSH`), a listener (local: `net.Listen` on the WRM machine → `client.Dial`; dynamic: a small SOCKS5 server (CONNECT, no auth) → `client.Dial`; remote: `client.Listen` (`tcpip-forward`) → `net.Dial` on the WRM side), per-tunnel counters, a 30 s keepalive and automatic reconnect with backoff while the listener stays open. `connect` tunnels are reference-counted by the terminals of the connection (`holdConn` / `releaseConn` with a grace period); `always` tunnels start after the database at boot. Changes are pushed to the owner's browsers through `/ws/events` (`tunnels_changed`). Policies are checked when a tunnel is saved, started, and again when a policy changes (`applyPolicy`).
- **Remote desktop** (`guac.go`): RDP, VNC and Telnet go through guacd. `/ws/desktop` authorizes the connection like a terminal, opens a temporary tunnel through the jump hosts when needed, connects to `guacd_address`, performs the handshake (`select` → `args` → `size`/`audio`/`video`/`image`/`timezone`/`connect` → `ready`) with the stored parameters (`connections.options`, JSON) and then relays complete instructions: guacd → browser in batches (recorded to `recordings/…/<uid>.guac.gz`), browser → guacd only allow-listed opcodes. Sessions use `terminal_sessions` (`protocol` rdp/vnc/telnet) and `session_recordings` (`format` `guacamole+gzip`); the browser replays them with `Guacamole.SessionRecording`.
- **Terminal backends** (`console.go`): the terminal WebSocket talks to a `termIO` (stdin, stdout, start, resize, wait, keepalive, close): an SSH shell, the serial console over the BMC's SSH (the console command is typed once the BMC prompt is quiet), IPMI Serial-over-LAN (`ipmitool sol activate` on the last jump host — the password goes over stdin after the wrapper turned echo off — or locally in a pseudo terminal, `tty_linux.go`), or a serial port of the WRM server (raw termios, `tty_linux.go`).
- **Out-of-band management** (`bmc.go`): `connections.bmc` holds a JSON BMC setting. Redfish requests use an `http.Transport` whose `DialContext` goes through the last jump hop when needed and whose TLS check pins self-signed certificates (`pinnedTLSConfig`, shared with FTPS, stored in `known_hosts` as `bmc://host:port`). IPMI runs `ipmitool` with `-E`, locally or on the last hop. Power actions map to Redfish `ResetType`s / `ipmitool chassis power`.
- **Quick connect & notes** (`quick.go`): a quick connection is an ordinary row in `connections` with `temp_until` set (RFC 3339, 24 hours after the last use). It goes through `normalizeConnection`, `validateJump` and `checkAuthRefs` like a saved one, is created with `monitor=0`, is excluded from export, and `touchQuick` moves `temp_until` whenever a terminal or desktop opens it. `runQuickCleanup` deletes expired rows every 10 minutes unless a terminal of the connection is open; `PUT … {temporary: false}` clears `temp_until`. `connections.notes` holds the owner's notes; lists only return `has_notes`, `GET /api/connections/{id}` returns the text, the browser renders a small markdown after escaping everything.
- **Network tools** (`nettools.go`): `POST /api/nettools` validates the target (host name / address characters only), takes a per-user lock and runs the tool either on the WRM server (`net.Dial`, `exec.CommandContext` with arguments, no shell, `net.Resolver`, `http.Client`) or from a source connection of the user through `dialSSH`: port and HTTP checks use `client.Dial` (`direct-tcpip`) so nothing runs on the server, ping / traceroute / DNS run a fixed POSIX script with the shell-quoted target (`runRemoteScript`). The HTTP check does not follow redirects and verifies the certificate separately against the system roots to report trust without failing.
- **Installable app** (`pwa.go`): `/manifest.webmanifest` and `/sw.js`. The service worker cache is named after `AppVersion` (`wrm-<version>`), precaches the vendor scripts and brand files, serves `/static/` cache-first, never touches `/api/` or WebSockets, and falls back to an offline page for navigations when the server is unreachable.
- **Tags & inventory** (`inventory.go`): `connections.tags` holds normalised, comma-joined tags. CSV files are decoded (UTF-8 / UTF-16 / Windows-1250) and split with `encoding/csv` after separator detection; `.xlsx` workbooks are read with `archive/zip` and `encoding/xml` (workbook, relationships, shared strings, sheet). Rows become `importItem`s through a field → column mapping and go through the same `importer.commit` as the mRemoteNG / OpenSSH imports. NetBox objects are fetched page by page (`/api/dcim/devices/`, `/api/virtualization/virtual-machines/`), get `ext_id` `netbox:<host>:<kind>:<id>` and `ext_tags` (the tags NetBox controls), so a later import updates them instead of duplicating; `inventory_sources` keeps the address and the encrypted token per user.
- **SSH key store** (`keys.go`): table `ssh_keys` (owner, type, public line, encrypted private key, fingerprint) and `ssh_key_deployments` (key ↔ connection). Connections with `auth_method` `KEY_REF` point to a key (`connections.key_id`). Deploy / revoke / "who has access" log in with `dialSSH` and run small POSIX `sh` + `awk` scripts (`runRemoteScript`) that read the key or its base64 blob from stdin and change `~/.ssh/authorized_keys` in place.
- **Credentials vault** (`credentials.go`): tables `credentials` (owner, user name, encrypted password and pending password, optional `key_id`, host patterns, `shared_all`, rotation interval and status) and `credential_grants`. Connections with `auth_method` `CREDENTIAL` point to one (`connections.credential_id`). `loadConnection` calls `resolveConnectionAuth`, which replaces `KEY_REF` / `CREDENTIAL` by `KEY` / `PASSWORD` with the decrypted secret after checking ownership, grants and host patterns (for grantees also the jump hosts); `dialSSH` resolves every hop the same way, and a failure is kept in `authErr` and reported at login. Rotation (`startRotation` / `runRotation`) runs in the background: pre-flight logins, `passwd` over a PTY per user@host, verification, rollback; the browser polls `/api/credentials/{id}/rotation`.
- **Snippets** (`snippets.go`): table `snippets` (owner, scope all/folder/connection, `auto_run`, `shared`). Variables are expanded per terminal (browser for manual use, server for run on connect). `ssh_ws.go` types run-on-connect snippets into stdin once the first output has been quiet for 400 ms (at most 5 s after the shell started).
- **Folder bookmarks** (`bookmarks.go`): table `bookmarks` (owner, name, path, scope global/folder/tag/connection, `start_dir`, `shared`, sort). The server expands the path variables (`{host}`, `{name}`, `{user}`, `$USER`) per connection and builds the shell-quoted `cd -- '<path>'` (a leading `~/` stays unquoted); the browser never builds the command. The start directory bookmark (most specific scope) is typed by `ssh_ws.go` before the run-on-connect snippets, and the file manager opens there; `files.go` resolves `~/…` against the SFTP home / FTP login directory. Share participants get only the owner's shared global bookmarks.
- **Broadcast input** is done by the browser (`termInput` sends the same keystrokes to every terminal of the group); each terminal WebSocket receives a `broadcast` control message so the server can audit it per terminal session and refuse it when `broadcast_enabled` is off.
- **Live status** (`status.go`): `statusMonitor.round()` loads all monitored connections (effective route), builds one target per host:port (per proxy and host:port with a proxy, or per jump host and host:port when `status_jump_checks` is on), probes them with 32 workers (TCP connect, SSH/FTP greeting, one retry), keeps state and "since" per target, derives the state of connections behind jump hosts from the jump host, and sends `status_changed` to owners whose connections changed. Transitions to down (from up, or from unknown behind a jump host) and from down back to up are passed to `notifyStatusChange` for the owner.
- **Git workspace** (`git.go`, `git_source.go`, `git_bundle.go`, `git_scan.go`, `git_monitor.go`; UI in `static/git.js`, loaded by `openGit()` on first use): everything is per user. `git_sources` (GitLab / GitHub / Gitea with an encrypted token, or an imported bundle whose `bundle.json` is kept in `info`), `git_trees` (path → blob ID per source, project and commit; immutable, cached forever), `git_blobs` (per source and blob ID: normalised SHA-256 with CRLF → LF, the hash with every CR removed, size and content up to 8 MB; bundle payloads use `sha256:<hash>` as blob ID), `git_workspace` (catalog JSON, settings, last check), `git_targets` (resolved ref and files with per-file history per service) and `git_installs` (server, path, environment, state and the last comparison as JSON). `gitProvider` talks to GitLab API v4 / GitHub REST / Gitea API v1 (pinned TLS for self-signed servers, no redirects to other hosts); `computeTarget` resolves the ref (branch-aware tags from the branch's last 500 commits, numeric version sort, fallback branches), lists the trees of the target and the earlier tags, fetches only unknown blobs and builds the history. `checkServer` logs in once per server (`dialSSH`), runs a `find` over the roots for the fingerprint files (`discoverOn`) and a hashing script (`scanOn`: `tr -d '\r' < f | sha256sum`, `VERSION.md`, `grep` of systemd / supervisor unit files), and `compareInstall` derives the file and installation states. `runGitMonitor` checks users with periodic checks on every `git_check_interval_minutes` and passes new versions, drift and unreachable servers to `notifyUser` (events `git.new_version`, `git.drift`, `git.unreachable`). API: `/api/git`.
- **Git files and check jobs** (`git_files.go`, `git_jobs.go`): `listInstallFiles` runs one `find` over an installation (`listOn`: prunes plus the catalog's `ignore_dirs`, `stat -c` / `stat -f`, the check's hash, symlinks with `readlink`, unreadable files and directories, at most 10 000 entries) and joins it with the repository at the target (`openRepoView`: the target's files plus the cached tree of `commit_full` below the subdirectory); `catalogReason` names why a file is (not) compared and `trackedState` (shared with `compareInstall`) gives tracked states. Untracked repository files are compared through `git_blobs` (`ensureBlobs`, at most 200 per listing) and never affect the installation state. `readServerFile` reads one file with `cd` + `pwd -P` (no path out of the installation, no symlink) for `viewInstallFile` and `installDiff` (any repository file except protected ones). `installCommits` uses `gitProvider.compareCommits` (GitLab `repository/compare`, GitHub `compare/a...b`). A check job (`gitCheckJob`, in memory, one per user under `gitLock`) resolves installations, servers, stale or never-checked selections (`planGitJob`), logs in once per server, optionally discovers, then scans every installation on its own session (`scanOn`) bounded by `git_check_per_server` and `git_check_parallel`, saving each result at once (`saveInstallResult`; `saveInstallError` keeps the last good files, `git_installs.last_ok_at` / `last_ok_state`). The browser polls `GET /api/git/check/jobs/current?since=<seq>` and gets the installations finished since; cancel closes the job's SSH clients so running scans are dropped unsaved.
- **Git runs** (`git_runs.go`, `git_deploy.go`): `git_runs` holds every run (kind update / upgrade / rollback / stamp / restart, state, the request with the **pinned targets**, the per-installation results, scheduled / started / ended times, the notice time) and `git_pending_restarts` the installations updated without a restart. `createGitRun` validates the request (policy per kind, ownership, the typed server name for production installations, restart choice, schedule), pins the targets (`upgradeTarget` computes a target at another ref, cached for 30 minutes between plan and run), stores it and either starts it (`startGitRun`: one running run per user, progress in memory in `gitLive`) or leaves it *scheduled*; a restart at a time or after a delay is a child run waiting for its parent (`releaseChildRestarts`). `executeGitRun` works on the installations in order and stops at the first failure. Per installation (`deploySession`, one SSH login): `scanOn` + `planFiles` + `selectRunFiles` (fresh comparison, default old + missing, ticked local changes only), `prepare` (host, user, owner, tools, line endings, Python import lines via `awk`), `danglingImports`, `makeBackup` (`mkdir` claims `<install>/.deploy-bak/<id>-<time>`), `stage` (temporary file per file, copied from the old one, content on stdin, verified with the `tr -d '\r' | sha256sum` hash), `commit` (renames, deletes), `checks`, `restore` on failure, `versionMD` / `pyJSONLine` + `appendUpdateLog`, then `refreshInstallState`. `restartUnits` restarts and health-checks units. `runGitScheduler` marks runs interrupted by a stop, then every 20 s (`gitSchedulerTick`) starts due runs, skips runs older than `git_schedule_grace_minutes` and sends `git.job_upcoming` 15 minutes before. Events `git.deploy_started`, `git.deploy_done`, `git.deploy_failed`, `git.restart_scheduled`, `git.restart_done`; audit `git.update`, `git.upgrade`, `git.rollback`, `git.restart`, `git.stamp`, `git.run_scheduled`, `git.run_cancelled`, `git.run_skipped`.
- **Git install and transfer** (`git_provision.go`, `git_template.go`): runs of kind *install* / *transfer* (policies `git_install`, `git_transfer`; never scheduled; restart choice none / now). `createProvisionRun` validates the request (`validInstallDir`, the per-host file choices against the pinned target, the unit, the typed server name for production targets and overwrites), stores it **redacted** (`redactedProvision`: no typed values or contents, vault references only) and starts it with the full request in memory. `gitPrepare` (`POST /api/git/provision/prepare`) resolves the targets (`installTarget`: the stored target, a bundle, or another ref via `upgradeTarget`), the per-host slots (`installSlots`: templates by name — `templateDest` — with their fields from `templateFields`, protected files of the repository, literal protected names and the protected files of other installations) and runs `precheckDirs` (one script: exists / files / `VERSION.md`, nearest existing parent, writable, `df -Pk`, owner, `python3` / `node` / `tar`). Install: contents from `gitFileContent` plus the filled files (`fillTemplate`, `vaultValue` with the credential's host list, `readInstallFile` over SSH) are packed with `tarOf`; transfer: `listForTransfer` (hash and size per file) and `transferSelection` / `transferExcluded`, then `runRemotePipe` streams `tar -c` on the source into the target. Both unpack with `receiveScript` into `<dir>/.wrm-incoming-<run>` and verify the hashes (`verifyStaged`); `placeStaged` backs up replaced files (`makeBackup`), creates directories, renames (`commit`), runs the checks and rolls back (`restore`) on failure. Then `VERSION.md` (`versionMD`, or `retargetVersionMD` for a transfer), the `updates.jsonl` line, `register` (a `git_installs` row added by hand, `createUnit` for the optional systemd unit / supervisor program as root or with `sudo -n`, `refreshInstallState`); a start uses the restart step of the runs. Audit `git.install`, `git.transfer`.
- **Git .gitignore helper** (`git_gitignore.go`, the *.gitignore* tab of `static/git.js`): `gitIgnoreState` gathers per service the *extra* files of the stored comparisons (`extraCandidates`, sizes from `scanOn`'s `wc -c`, `suggestIgnorePattern`), reads the head of the service's branch (`readRepo`: `branchCommits`, the cached `tree`, the `.gitignore` blob), detects stacks (`detectStacks`) and secret / protected files (`gitIgnoreWarnings`, template names like `templateDest` reads them). `mergeGitignore` appends new patterns only (line endings kept); preview diffs with `unifiedDiff`; the download is the default. `createGitignoreMR` uses the source's **write token** (`git_sources.write_token`, `newGitWriteProvider`, `gitProvider.send`): GitLab `repository/branches` + `repository/commits` + `merge_requests`, GitHub `git/refs` + `contents` (with the blob SHA when the file exists) + `pulls`. Policy `git_gitignore_mr`, the typed project checked by the server, audit `git.gitignore_mr`.
- **Git environments** (`git_env.go`, `git_env_run.go`, the *Environments* tab of `static/git.js`): `gitCatalogApp.Environments` (ordered destinations `{server, path}` resolved by connection name with `envConn`, `confirm`, `allowed_refs` via `refAllowed`, `ignore`, `post_deploy`, `keep_backups`, `state_dir`), validated in `normalizeEnvs` and `checkEnvPaths` (nested app paths unless excluded, state directories inside app paths). `envPlanRequest` resolves the target (`installTarget`), checks `allowed_refs` and computes a `gitEnvDestPlan` per destination (`envPlanCtx.destPlan`: one `envScanScript` per destination — CR-stripped hash, CR count, symlinks, unreadable files, `VERSION.md`, `state.json`, the lock — classified as new / changed / eol / same / removed (in the tree of the deployed commit, `previousTree`) / extra / protected / ignored, type conflicts, warnings, `fingerprint`); plans are kept in memory (`gitEnvPlans`, 2 hours) and used once (`takeEnvPlan`). Runs: `createGitRun` hands requests with `env` to `createEnvRun` (typed environment name, `post_deploy` pinned, plan used once, exclusions remembered in `git_env_exclusions`); `executeGitRun` calls `envDeployItem` / `envRollbackItem`. A deploy item: `envLock` (mkdir `<state>/.lock` + owner file, server time) → `destPlan` again and the fingerprint compare → `envSelection` → `envProbe` → `tarOf` + `receiveScript` (`gitTransferTimeout` ≥ 1 h; `envPartial` records an interrupted transfer) → `verifyStaged` → `envBackup` → `envCommit` (stdin lists: deletes with removed directories, then renames keeping mode / owner) → `envChecks` → manifest `deploys/<id>.json` and `state.json` (`envWriteFile`), `updates.jsonl`, optional `post_deploy`, `envAppendHistory`, `envPrune`, `envRegister` (a `git_installs` row) → `envUnlock` (own id only). A rollback item checks `state.json` / the manifest / the backup under the lock and runs `envRollbackScript` (added files and current versions moved to `backups/rollback-<id>/`, removed directories re-created, symlinks skipped, `DRY=1` for dry runs). `envBreakStale` removes a stale lock (max(30 min, transfer timeout)) after checking it again on the server. `envCell` (lazy overview cells, commits behind via `compareCommits`, drift), `envHistory` and `envDoctor` read the destinations in parallel (`forEachDest`). API: `apiGitEnv` under `/api/git/env/…`; audit `git.lock_removed`, `git.exclude_added`.
- **Git activity, deploy history and "what is where"** (`git_activity.go`, `git_where.go`, the *Activity* tab of `static/git.js`; read-only, no schema change): `fetchActivity` resolves the service's source (`serviceSource`: the target's source, else the workspace's API source) and lists GitLab push events (`/events?action=pushed`) and per-branch commits (`branchCommitsIn`; GitHub also `/activity`, `githubPushes`) for the chosen or tracked branches (`trackedBranches`); `apiWalk.list` follows `Link: rel="next"` / `X-Next-Page` / cursors up to `gitActivityPages`, stops when `RateLimit-Remaining` / `X-RateLimit-Remaining` ≤ `gitActivityRateFloor` and turns HTTP 429 / 403-without-calls into notes (`isRateLimited`, `rateReset`). Listings are kept in `gitShortCache` (per user, source, service, branch and dates, `gitActivityTTL`); `gitActivity` applies the author filter and `summarize` builds the per-author and per-branch summaries; `gitWeb` builds commit / compare / branch links per provider. The deploy history merges `envHistory` per (service, environment) (`envHistoryRows`, cached `gitWhereTTL`, policy `git_checks`) with `runHistoryRows` (git_runs without `env`) and filters them in `gitHistoryFilter.match`; the matrix (`whereEnvCell`) extends `envCell` with the branch head (`gitProvider.branchHead`), commits behind it (`behindCounter`: one compare per distinct commit, cached) and drift (`markDrift`), plus installations without environment from their last check (`whereInstalls`). CSV: `writeCSV` (BOM, `csvCell` neutralises formulas). API: `apiGitActivity` (`/api/git/activity…`), `apiGitWhere` (`/api/git/history/…`, `/api/git/where/…`). Gitea is a third API kind (`gitAPIKind`, `gitProvider.hub()` for the GitHub-style REST shared with GitHub, `pageQuery` with `limit`, `giteaTree` for the paginated tree).
- **Git CI integration** (`git_ci.go`, opt-in): webhooks — `git_sources.hook_id` / `hook_secret` (encrypted) / `hook_at`; `gitHookHandler` at `/api/hooks/git/` (exempt from the CSRF check in `securityMiddleware`, body limit 5 MB) rate-limits per hook and client address (`hookAllowed`), authenticates (`verifyGitHook`: GitLab token, GitHub HMAC, generic token or timestamped HMAC; constant-time compares), refuses replays (`hookSeen`, delivery IDs for 24 h), maps the project to services (`hookServices`) and queues `runHookCheck` per user (`queueHookCheck`: one worker, deliveries merged; `refreshTargets` + `runGitCheck` on the servers of those installations + `notifyGitRound`). Artifact feeds — table `git_feeds` (URL, header name, encrypted header value, interval, last hash, the bundle source); `fetchGitFeed` downloads with `ciClient` (pinned TLS, no redirects to another host), skips an unchanged hash and imports with `importBundle`, replacing the feed's previous bundle; `gitFeedsTick` runs on the Git scheduler's tick. CI pipelines — table `git_pipelines` (per user and service: kind, URL, project, ref, user, encrypted token); `createGitRun` marks update / upgrade items of such services `via: ci`, `executeGitRun` calls `pipelineItem`: `triggerPipeline` (Jenkins `buildWithParameters` → queue item → build; GitLab `trigger/pipeline`) and `pollPipeline` every `gitCIPollEvery` until a result (`gitCIPollTimeout`), URLs returned by CI moved onto the configured host (`onHost`); the item keeps `ci_kind`, `ci_url`, `ci_status`; afterwards `refreshInstallState` when SSH works.
- **Notifications** (`notify.go`): `notify_channels` (kind, JSON config with secret fields encrypted, `user_address`, last delivery / error), `notify_subscriptions` (user × event × channel, optional own recipient), `notify_prefs` (quiet hours, time zone, language), `notify_pending` (queued messages) and `notify_state` (reminder state). `notifyUser` stores one row per subscribed channel; the `notifyDispatcher` (every 2 s, poked on new rows) groups rows per user, channel and recipient, waits `notifyDebounce` after the newest one (one status round → one digest), honours `notify_min_interval_seconds` and the user's quiet hours, sends with the channel's sender (SMTP via `net/smtp` with STARTTLS / TLS; Telegram, Slack-format, Teams Adaptive Card, Discord, ntfy, Gotify, Pushover over HTTPS; a generic JSON webhook signed with `X-WRM-Signature: sha256=HMAC`) and retries failures with backoff (dropped after 6 attempts). `checkCredentialReminders` (hourly, and after a rotation) emits rotation due / incomplete to the credential owner. API: `/api/notify`, `/api/admin/notify/channels`.
- **Web interface connections**: protocol `HTTP` / `HTTPS` with `web_path`. `POST /api/connections/{id}/open-web` returns the URL directly, or — behind a jump host — opens a temporary local tunnel over the last hop (30 minutes idle limit) and returns its URL.
- **Import** (`importers.go`): mRemoteNG `confCons.xml` (AES-GCM with PBKDF2-HMAC-SHA1 key / legacy AES-CBC with MD5 key; `Protected` check of the master password; full-file encryption; inheritance; `SSHTunnelConnectionName` → jump host) and OpenSSH config (`Host`, `Host *`, `ProxyJump`, `ProxyCommand ssh -W`, `*Forward`, `IdentityFile`). PuTTY sessions (`putty.go`): a `.reg` export (UTF-16 LE / UTF-8), URL-decoded session names, *Default Settings* as defaults, SOCKS4 / SOCKS5 / HTTP proxies saved as proxies (deduplicated by type, address, login and DNS setting), *SSH proxy* → jump host. All go through one `importer` that skips duplicates, links jump hosts by name, creates or reuses proxies and validates tunnels. Imported PuTTY sessions are remembered with their proxy in `putty_sessions`; mRemoteNG connections keep the session they name in `connections.putty_session`, so the proxy is linked whichever file is imported first.
- **Server-to-server SFTP**: `transferRemoteHandler` in `main.go` opens SFTP to both servers from WRM and copies through a 1 MiB buffer, streaming NDJSON progress to the browser.

## Stored connections and credentials

- `connections` (host, port in `host`, username, auth method, `password`, `private_key`, `key_path`, `key_id`, `credential_id`, folder, owner `user_id`, `jump_conn_id`, `web_path`, `tags`, `ext_id` / `ext_tags` for inventory sync), `connection_tunnels` and `folders`. This is the "servers" inventory of the plan. Keys of the key store (`ssh_keys`) and vault credentials (`credentials`, `credential_grants`) are shared by many connections.
- Passwords, private keys and TOTP secrets are encrypted with **AES-256-GCM** before they are stored (`security.go`). The key comes from `ENCRYPTION_KEY`, `ENCRYPTION_KEY_FILE` or a random key file `<DB_PATH>.key` (mode `0600`), never from the database or git.
- Secrets are never returned by the API: the UI only "sets/replaces" them. They are decrypted in memory when connecting. The only exceptions are explicit, audited owner actions after re-authentication (config export with secrets, private key export, *Show* of a vault password), all behind the `allow_secret_export` policy.
- Server-side key files (`key_path`, `~/.ssh`) are limited to administrators by default.

## Canvas and collaboration

- The multi-window canvas (windows, tabs, snapping) is **client-side state**. Saved workspaces are stored on the server (`sessions` table, `/api/sessions`).
- **Sharing** (`shares.go`): `share_links`, `share_items` (connections/folders), `share_members` and `share_participants`. Five roles (observer, viewer, operator, moderator, owner) with permissions, enforced on every request by `authorizeConnection(r, connID, perm)`.
- **Realtime** (`collab.go`): `/ws/share/{token}` rooms. The server is the authority for identities, roles, presence, chat, terminal sharing (the sharer's browser streams output to watchers), keyboard control grants and voice signalling. `/ws/events` carries per-user notifications.

### Decisions where the plan's example names collide with existing code

- **`terminal_sessions`** instead of `sessions`, because `sessions` already stores saved workspaces.
- **`/api/recordings`** instead of `/api/sessions`, because `/api/sessions` is the workspace API.
- The plan's `servers` are the existing **`connections`** (each with an owner). Phase 2 adds grants on top of them.
- `audit_log` keeps its existing column names (`action` = the plan's `event_type`, `details` = `detail_json`, `ip` = `client_ip`) and gains `conn_id` (server), `session_id`, `prev_hash` and `hash`.
- Recordings are **gzip-compressed asciicast v2** files on disk (`WRM_RECORDINGS_DIR`, default `recordings/` next to the database). The checksum is the SHA-256 of the stored file. The API serves the plain `.cast`.
