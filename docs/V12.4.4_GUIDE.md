# v12.4.4 operation guide

## Monitoring and Functionality

Open **Monitoring** from the top bar. **Servers** shows hostname, connection name/id and folder context with CPU, memory, load, uptime, filesystem use, network rates, latest sample and history. **Functionality** contains the former Git service checks, Supervisor/systemd diagnostics and configuration/profile inspection. Its hostname groups combine server, service, environment, runtime, health, stale/never and installation-problem filters. **Logs** contains discovery, historical search and live panels. Search/filter controls stay inside the top of their scroll container.

Each owned SSH/SFTP connection has **Monitoring settings**:

| Mode | Required setup |
|---|---|
| Agent through SSH | Installed passive Zabbix agent/agent 2, SSH credentials already in WRM, reachable agent address on the SSH host; default `127.0.0.1:10050`. Allow that loopback source in the agent's existing `Server` list. |
| Agent through network route | Installed passive agent, configured address and authorized network/jump/proxy route. Its allowlist must accept the route's source. |
| TLS certificate | Trusted CA/server name and, where required, client certificate/key. WRM verifies the peer; there is no skip-verification switch. |
| PSK | SSH mode and an already installed remote `zabbix_get`, existing remote absolute PSK file and identity. The PSK file is never downloaded to WRM/browser. |
| Existing Zabbix API | HTTPS `api_jsonrpc.php` URL, API token with host/item read access, host id and configured agent template items. Works with data already collected from active-only agents. |

**Detect OS and installed agent** runs fixed read commands and displays the result. Setup guidance links official packages and explains allowlists/TLS. Installation/configuration remains a reviewed administrator operation using the normal authorized terminal/assistant workflow. WRM does not alter an existing Zabbix installation or open ports automatically.

The open server overview refreshes its displayed samples every 30 seconds while preserving its filter/scroll position. Automatic remote polling is opt-in, at 30–3600 seconds per server, with four workers and a two-minute poll deadline. History keeps at most 2880 samples per connection; a history response is at most 1440. Problem/recovery notifications use WRM notification preferences and state transitions. Missing/unsupported/old metrics stay unknown or warning; a reachable agent does not establish that every service is healthy. Network rates need two passive samples; API network items must declare byte-rate units. Actual item support depends on the remote OS/template. WRM supplies host metrics, not hypervisor administration.

Passive responses use bounded JSON/legacy Zabbix framing and bounded decompression (1 MiB). Discovery derives at most 32 filesystems and 16 interfaces. API polling is bounded to 500 items. Private keys/API tokens are encrypted in the per-connection monitoring profile; ordinary settings views omit stored secrets. Empty secret fields retain existing values.

## Log roots, filters and panels

In Monitoring settings enter one root per line:

```text
/var/log | system | demo-operator
/srv/demo-api/log | demo-api | demo-operator
/srv/demo-worker/log | demo-worker | demo-operator
```

Roots must be absolute directories other than `/`. Discovery stays inside configured roots, rejects symlink components, caps traversal at depth 8 / 10,000 entries / 2000 files per server and shows incomplete/permission warnings. It reads with the same SSH account and WRM file/share permissions; configuring a root grants no extra remote privileges.

Choose server, service, operator and logs, then optional time range, timezone and literal keyword. ISO/RFC3339, naive ISO and syslog timestamps are supported; naive timestamps use the chosen IANA timezone, syslog uses the current year, and continuation lines inherit the preceding timestamp. Unknown timestamps remain visible and are counted. Date filters are interpreted in the selected log timezone, not silently in server local time.

**Read** opens a bounded excerpt. **Search file from the beginning** scans a segment, then **Next segment** continues using the returned byte cursor; this searches older content without downloading an entire large file. A segment scans at most 8 MiB and returns at most 256 KiB / 2000 matching lines. Physical events crossing segment boundaries may require examining the adjacent segment. Binary/compressed logs are explicit unsupported text inputs; unpack them through a separately authorized operation first.

**Follow selected** opens up to 16 independent panels. Drag a title, resize a corner, tile vertically/horizontally or cascade. Bring a panel forward by clicking its visible area. Select recent 5/10/50/2000 lines, pause/resume, toggle autoscroll, navigate highlighted matches, copy or download the displayed excerpt. **Open terminal here** opens the log directory on the same server. **Open log in terminal** follows its last 100 lines with a literal path using POSIX `tail` or PowerShell `Get-Content`; the log must stay inside a configured monitoring root. Terminal/share permissions still apply. Live views refresh a bounded recent tail every two seconds; rotation/truncation/content changes produce a gap/reset notice. Poll failures reconnect, permission removal pauses, and closing a panel aborts outstanding reads. This bounded tail is not a lossless log archive; use the historical cursor for older content.

## GitLab through a client computer

1. Configure a GitLab source and the repository catalog in **Git → Settings**. Open **GitLab through this computer**, enable client access, and optionally name explicit WRM cache members. A member can contribute/read that source's owner-catalog snapshot, not modify its source configuration or obtain its stored server tokens.
2. Save and reload WRM to apply its browser connection policy. Enter a GitLab token with `read_api` and repository access on the computer that can reach GitLab. The token stays in browser memory; it is cleared on cancel/page exit. Every new authorized client Connect/check starts a refresh, and Git Check/Refresh refreshes connected browser contributors first.
3. Allow GitLab CORS/preflight for the WRM origin and `PRIVATE-TOKEN`, expose pagination response headers, and satisfy HTTPS/private-network browser rules. If blocked, prepare a companion job, download its short-lived relay key and run the WRM binary on that computer:

```sh
./wrm -gitlab-relay \
  -url 'https://wrm.example.com/gitlab-relay?job=JOB_FROM_WRM' \
  -gitlab-url 'https://git.example.com' \
  -relay-key-file wrm-relay-key.txt \
  -gitlab-token-file gitlab-token.txt
```

On Windows replace `./wrm` with `.\wrm.exe` (or the actual downloaded executable name) and use PowerShell's one-line form. Keep both local files private and delete the relay-key file after the job. `-ca-file` supports an internal GitLab CA. `WRM_RELAY_KEY` / `WRM_GITLAB_TOKEN` are optional environment alternatives; command-line token values are not used. The companion opens no listener, refuses other GitLab origins/catalog endpoints and redirects, and requires HTTPS WRM except loopback. It can remain connected for uncached read requests until the 30-minute job expires; `-relay-live=false` exits after one complete synchronization.

Snapshots cover the owner's 1–100 catalog projects, up to 200 refs/project, newest 500 commits per branch and up to 50 historical trees per branch, with 50,000 files/tree, 10,000 API requests, 8 MiB per response/blob and 256 MiB snapshot data. The browser and companion stop consuming responses above the byte budget, including unknown-length streams. Any exceeded limit or failed authorization makes that refresh incomplete and leaves the prior complete snapshot active. Git blob hashes are checked on WRM. New snapshots publish in a transaction with a monotonic generation; older late completions cannot replace newer successful data. Metadata shows generation, contributor, time, complete/live state and >24-hour staleness.

The encrypted server cache persists across client disconnect/restart. Current/previous API generations are retained; existing immutable tree/blob and reviewed deployment content remain in their normal caches. Advance an existing review only by reviewing again: Advanced plans return a two-hour owner/installation/action/ref-bound ticket and pin its full target manifest, while Simple/environment plans keep their existing fingerprints.

This is a repository **API read** relay. Native Medium Git clone/build/config Git subprocesses and GitLab mutations/pipelines/pushes still require a direct route and their existing approvals. Uncached data needs an attached client or a new snapshot; it is never fetched silently through a missing WRM route. The companion is a fallback for restricted browser networking, not an arbitrary TCP router.

## AI and MCP

### Provider request timing

| Setting / environment override | Default | Range |
|---|---:|---:|
| `ai_provider_header_seconds` / `WRM_AI_PROVIDER_HEADER_SECONDS` | 900 | 30–7200 |
| `ai_provider_request_seconds` / `WRM_AI_PROVIDER_REQUEST_SECONDS` | 3600 | 60–14400 |
| `ai_provider_stream_idle_seconds` / `WRM_AI_PROVIDER_STREAM_IDLE_SECONDS` | 600 | 30–7200 |

The first wait includes local provider loading/queueing/prompt evaluation; the total includes the entire generation, and stream inactivity counts time without response bytes. Stop/session cancellation closes the HTTP request. Diagnostics distinguish header, total and idle limits. WRM does not retry the assistant turn automatically or repeat its actions.

### Connecting apps

Use **Settings → AI connections**. The wizard includes read-only, approval and **Automatic within limits**, with explicit command/path/time/action opt-in. MCP remains off by default; administrator/per-connection restrictions still apply.

Codex offers OAuth sign-in or a bearer-token environment variable. Download `.sh` / `.ps1` setup scripts for Codex, Claude Code or Gemini CLI. Run them on the app's computer: they detect the selected CLI, add/list WRM and, for Codex, back up existing TOML first. Tokens are prompted locally and are absent from downloaded scripts. The Codex PAT script starts the client in that token environment; closing it clears that process environment. Vendor CLIs may store headers in their own user configuration. Cursor has its documented install link. Other clients retain generated instructions/config snippets.

Cloud ChatGPT/Claude connectors need an administrator-provided reachable **HTTPS** WRM MCP URL with OAuth/reverse-proxy setup. A browser endpoint check proves reachability from that browser only; it does not prove cloud reachability. `localhost` is appropriate only for a client on the WRM host. Setup scripts do not publish a local server or change the host's firewall.

**Edit** an active grant to change servers, mode, scopes and auto limits. Bearer hash/expiry remain; all its old MCP sessions/approvals terminate and the same token can initialize a new session. Every action checks current policy. Scope removal cannot keep an old cached tool authorization.

In WRM assistant, `/wrm` or `/wrm server` opens the authorized server picker. MCP exposes the `wrm` prompt and `select_server` tool; clients with form elicitation render the picker themselves. Other clients receive the same permitted server list as text. Slash-command spelling/menus depend on the client; WRM cannot register a global native command in every external app.

For `.ini`/`.py` inventory, use `inventory_files` with absolute path, extension filter, optional literal `grep` and limit. It uses SFTP, not a rewritten shell search, and retains unreadable/sensitive-path restrictions, symlink rejection, output/content/traversal/deadline bounds and redaction. The default is 500 files, maximum 3000, depth 12 / 10,000 entries, 256 KiB per searched file. An insufficient grant must be edited explicitly.

### Selected context and terminal startup

Terminal right-click offers Copy, Paste, Open terminal here and AI selection where permitted. Shift + right-click retains the browser menu; input/editor menus are not intercepted. Clipboard denial offers keyboard/native-menu fallback.

Selection-to-AI reads at most 32 KiB input / 8 KiB previewed text and applies redaction and sensitive-path checks before showing it. Review the server/path/context and enter the question; it is queued in the assistant as untrusted context under the existing connection/share/provider policy. Files are read through SFTP without following symlink components. The selection is not executed as a command.

Open terminal here uses the same server/share/route and a separate directory field. POSIX shell quoting and Windows PowerShell literal-path/encoded startup prevent filename text from becoming shell code; NUL/newline and oversized paths are rejected. Windows-via-SSH auto-detection uses a fixed OS probe. Actual shell availability and SSH account privileges still determine whether startup succeeds.

## Labels, imports and replay

Folder/connection edit forms provide color, 18 curated system/network/storage/security/OTT icons, preview and default/reset. Values are validated and owner-bound in an additive table; labels survive duplication and configuration export/import. Existing folder ordering remains available.

The general configuration import now routes mRemoteNG XML (including namespace/UTF-16) and PuTTY registry exports to their existing specialized importers. Native WRM JSON is still supported. Master-password prompts and unsupported/proxy notes remain visible. A synthetic 4 MiB XML and UTF-16 PuTTY export were checked in the browser; an arbitrary private export is not guaranteed to contain only supported vendor fields.

Replay scales terminal width, including very wide recordings, to the available screen. Existing recorded resizes/font loading/fullscreen observation remain active; graphical replay subtracts its container padding when fitting.

## API additions

All `/api` routes retain WRM session/CSRF authentication and the relevant owner/connection/share/policy checks. `/gitlab-relay` uses only its short-lived job-specific bearer capability.

| Route | Purpose |
|---|---|
| `GET /api/monitoring` | Owned connection/config/sample overview |
| `GET/PUT /api/monitoring/config?id=ID` | Read / owner configure monitoring and log roots |
| `POST /api/monitoring/check?id=ID` | Owner bounded metrics poll |
| `POST /api/monitoring/detect?id=ID` | Owner fixed OS/agent detection |
| `GET /api/monitoring/history?id=ID` | Bounded sample history |
| `GET /api/monitoring/logs?id=ID` | Discover configured log roots |
| `GET /api/monitoring/log?id=ID&root=ROOT&path=PATH` | Bounded tail/offset/scan/time/keyword excerpt |
| `GET/PUT /api/git/client/ID` | Client-cache status / owner settings and members |
| `POST /api/git/client/ID/start` | Authorized scoped refresh job |
| `GET/POST/DELETE /gitlab-relay?job=JOB` | Client work queue / response / cancel |
| `PUT /api/mcp/grants/ID` | Owner edit existing active grant |
| `POST /api/ai/context?id=ID` | Authorized bounded/redacted selected context |
| `POST /api/ai/servers` | Filter candidate IDs by assistant permission |

MCP adds `prompts/list`, `prompts/get`, `select_server` and `inventory_files`. Git plan items include `review_id`, which Advanced run items echo for immutable reviewed content.
