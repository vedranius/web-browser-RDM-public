# v12.4.5 operation guide

## Medium: ZIPs and one setup button

Open **Git → Medium**. Choose your trusted original deploy-tool ZIP and deploy-config ZIP; optionally add an SSH profile ZIP. Click **Prepare and run trusted ZIPs**. Empty fields reuse existing imports. The button authorizes running the uploaded trusted code/configuration and preparing its host dependencies.

WRM retains approved files privately, starts installed Docker, prepares the original lockfile, validates config, synchronizes the private profile and launches the original interface. Background setup survives browser disconnect; return to Medium for phase/status/error information. Resume after failure with empty ZIP fields. Stop active instances before replacing imports. Individual import/runtime/preference controls remain under Advanced setup.

An uploaded local config explicitly selects that ZIP instead of an older config Git repository. The repository working data remains private; reconfigure its repository in Advanced settings when desired. Original source, deployment plans/builds/confirmations/backup/history/rollback behavior remain unchanged.

### First Windows setup

Interactive Windows WRM can download the official Docker installer from HTTPS Docker domains. Downloads are limited to 1 GiB and require valid Authenticode/Docker publisher verification before launching the per-user WSL 2 installer. No accept-license or reboot flag is passed. Complete vendor/OS dialogs on the **WRM host**. Policy, WSL/virtualization or restart requirements can prevent completion; imports remain saved for resume.

Installed Docker uses `docker desktop start`, with the standard desktop executable as Windows fallback. Linux tries installed Desktop/user/system engine startup using existing privileges; macOS can launch installed Docker. Readiness waits up to three minutes; setup has a 30-minute total deadline. Windows services cannot display the installer: install Docker once for the execution account interactively. Docker context/engine are not switched and unrelated containers are not stopped. Select Linux containers explicitly if Windows-container mode is active. Linux without installed Docker/native prerequisites needs initial administrator package setup.

Vendor requirements: [Windows installation](https://docs.docker.com/desktop/setup/install/windows-install/), [startup CLI](https://docs.docker.com/reference/cli/docker/desktop/start/). Native Windows/PowerShell runtime installation was not exercised in this release.

## Understand Monitoring

- **Servers:** CPU/RAM/load/filesystem/network metrics need a configured installed Zabbix agent or existing Zabbix API. Unknown metrics are distinct from service failures.
- **Functionality:** service/config checks use existing WRM catalog/installation records and SSH permissions. Refresh with a service check; no Zabbix agent is needed.
- **Logs:** SFTP discovery/search uses the same account and file permissions, independently of Zabbix and full Git comparisons. Panels appear only in Logs; terminal actions close Monitoring.

## Automatic log discovery

Open **Monitoring → Logs**, then choose a server. Discovery starts automatically and publishes each server as it finishes, with four workers. **Find logs** refreshes it. Progress, errors, missing roots, bounds and empty results stay visible. **Monitoring settings** edits the selected server's additional roots and service/operator labels.

Sources are explicit roots; saved installations' `log`/`logs` folders; readable Supervisor stdout/stderr log paths; and two-level service/operator metadata under catalog roots plus `/home/operators`, `/srv`, `/opt`. Example `/srv/demo-api/demo-operator/log` supplies labels before a Git comparison. Supervisor configuration is read as metadata, never executed.

Bounds: 100 roots, 300 candidate directories, 40 Supervisor files/directory at 64 KiB each; 45 seconds, 2000 files / 10,000 entries / depth 8 per server; 10,000 file entries retained in the UI. Regular log-like names (`.log` and rotations, `.out`, `.err`, syslog/messages/stdout/stderr) are offered. Arbitrary code/config files and symlinks are excluded. Directory entries supply size/modification metadata, avoiding per-file REALPATH round trips.

A one-hour memory catalog binds discovered roots to connection owner/root settings. Root changes invalidate it; restart/expiry requires discovery again. Content requests still check current authorization, sensitive paths and symlink components. No sudo/agent installation runs during discovery.

## Search and open results

1. Select server, optional operator/service and filename/server query.
2. Set From/Until and IANA log timezone. Event time determines matches; file modification time is separate. Reversed ranges are errors.
3. Enter a keyword and **Search all matching logs** or Enter. Date/keyword changes schedule search. Every matching file is searched from its beginning, beyond the recent tail.
4. Result tiles show hostname/connection, service/operator, path, modification time, matching count, matching event range and highlighted excerpt. Unknown-time lines are counted; continuation matches inherit their event timestamp.
5. **Open matching records** opens the excerpt panel; **Follow** opens recent/live content. Select multiple tiles and **Follow selected**; existing resize/move/tile/cascade, copy/download, match navigation and terminal actions remain.

Historical segments read at most 8 MiB and return 256 KiB / 2000 lines. Search rounds use three workers, 32 MiB / 64 requests per file and 90 seconds overall. **Continue search** resumes unfinished files; Stop cancels requests. Scope changes reject late results. Excerpts are capped at 256 KiB/file and disclose truncation; counts can cover more than the excerpt. An individual event exceeding the display limit can prevent cursor progress and stays explicitly incomplete; use the terminal/file-download workflow in that case. Compressed/binary logs are explicit unsupported text inputs; extract through a separately authorized action first.

Timestamp/syslog current-year behavior remains as in the [v12.4.4 guide](V12.4.4_GUIDE.md). Unknown-time lines are retained and do not establish a match inside the date range. Live panels are bounded recent-tail views, not lossless archives.

## Sticky controls and environments

Overview pins filters plus check/selection/progress controls. Installations also pins actions. On small screens the control stack can scroll inside its bounded height while data scrolls separately. Environments combines text/service/environment/server filters with reset and sticky refresh/status controls. Connection names/learned hostnames are searchable. Cell reads are deduplicated during typing; filter values survive refresh.
